# Aéza Analyzer — сценарий живой демонстрации

> **Историческая заметка (2026-10-24).** Файл написан для защиты вместе с
> презентацией и содержит числа прежней конфигурации (`expiry_proximity = 15,0`):
> балл клиента #10 **73,3** и выручка **5,74 €**. Текущая конфигурация
> (`expiry_proximity = 3,0`, окно 90 дней) даёт **71.4** и **5.80 €**.
> Команда запуска backend — `python -m uvicorn main:app` **из корня репозитория**
> (`app.main:app` из `backend/` падает с `ModuleNotFoundError: core`).
> Адреса вида `*.prod-runtime.all-hands.dev` — временные адреса песочницы, они
> больше не работают; актуальный стенд — <https://aeza-sentinel.pixel-minds.ru/>.
> Актуальные команды и устройство авторизации: `README.md`,
> `docs/PROJECT_GUIDE.md`, `docs/AUTH_MODULE.md`.

Обязательный сценарий организатора: **найти клиента под риском → объяснить причины →
показать денежную оценку → изменить коэффициент → показать обновление результата.**

Регламент: 4–6 минут доклада. Демонстрация встроена между слайдами 3 и 7.

## Подготовка за 10 минут до защиты

1. Поднять стек по README (backend + frontend) и убедиться, что снимок загружен:
   ```bash
   # из КОРНЯ репозитория (main.py лежит в корне, core.py тоже)
   export AEZA_DATABASE_URL="sqlite:///$(pwd)/data/analytics.sqlite"
   export AUTH_DATABASE="$(pwd)/db/auth.sqlite3"
   export AUTH_PRIVATE_KEY="$(pwd)/db/private_key.pem"
   export AEZA_ANALYTICS_FACTORY="backend.app.domain.module:create"
   export AEZA_SEED_DEMO_DATA=1
   python -m backend.users create analyst@aeza.test
   python -m uvicorn main:app --host 127.0.0.1 --port 8000
   # во втором терминале:
   cd frontend && npm install && npm run dev   # http://127.0.0.1:5173
   ```
   Полный стек с PostgreSQL — `docker compose up --build` (интерфейс `:8080`).
2. Открыть два окна браузера и войти под учётной записью, созданной вручную командой `backend.users create` (пароль задаётся в консоли и не хранится в конфигурации Compose):
   - окно A: демо-стенд — для показа (в текущей среде проверен
     `https://work-1-vllmnzyteekiqwpn.prod-runtime.all-hands.dev/`, HTTP 200);
   - окно B: тот же стенд — резерв, если окно A потеряет состояние.
   Адрес стенда временный: перед защитой подставьте актуальный URL и замените
   заглушку `[QR-КОД: ДЕМО]`.
3. Вернуть модель к значениям по умолчанию: `/settings` → **«Значения по умолчанию»**.
   Убедиться, что вес `expiry_proximity` = **3** и балл клиента #10 = **73,3**.
4. Открыть заранее во вкладках: `/customers`, `/customers/10`, `/settings`.
5. Проверить, что в шапке дашборда стоит опорный момент **19.10.2026, 15:00 UTC**
   и горизонт **30 дн.** Если дата другая — данные переимпортированы, числа будут
   отличаться от слайдов. Это единственный критичный параметр воспроизводимости.
6. Масштаб браузера — 100 %, окно на весь экран. Скрыть закладки и лишние вкладки.

## Сценарий по шагам

### Шаг 1. Найти клиента под риском — 40 сек

| Действие | Что говорите |
|---|---|
| Открыть `/customers` | «Список уже отсортирован по риску. Смотрим верхнюю строку.» |
| Показать строку `user-0010@example.test` | «Клиент #10: балл 73,3 из 100, категория высокий. Это максимум по базе — выбираем не случайно.» |
| Показать колонки «Услуги 3 / 3», «Выручка под риском 0,00 €» | «Три услуги, все пригодны для прогноза. Выручка под риском — ноль, объясню почему через минуту.» |

Слайд в этот момент: **04 «Клиент #10 — высокий риск, 73,3 из 100»**.

### Шаг 2. Объяснить причины — 60 сек

| Действие | Что говорите |
|---|---|
| Кликнуть строку → карточка `/customers/10` | «Открываем профиль.» |
| Показать метрики: балл 73,3, категория высокий, 1 из 3 услуг высокого риска | «Балл клиента — максимум по услугам, пригодным для прогноза. Среднее замаскировало бы одну критичную услугу.» |
| Блок «Причины оценки» по `service-0030` | «Вот почему: услуга просрочена на 35 дней, два продления из двух не выполнены, автопродление выключено.» |
| Нажать **«Показать все факторы (7)»** | «Формула открыта: 100 умножить на сумму вес×значение, делить на сумму весов. Здесь 11 из 15 — отсюда 73,3.» |
| Показать факторы с вкладом 0,00 | «Два фактора дали ноль: баланса хватает, услуга не приостановлена. Модель не накручивает риск там, где сигналов нет.» |

Слайд: **05 «Балл объясним: видно каждый вклад»**.

Ограничение, которое нужно сказать вслух: балл — не вероятность оттока, а индекс
rule-based модели. Исторических исходов ухода в снимке нет, поэтому точность не измерена.

### Шаг 3. Денежная оценка — 40 сек

| Действие | Что говорите |
|---|---|
| Показать блок «Выручка под риском 0,00 €» у клиента #10 | «Балл высокий, а денег под риском ноль. Все его сроки уже прошли: горизонт смотрит вперёд, а просрочка — в прошлом.» |
| Открыть `/` → таблица «Ближайшие продления в горизонте» | «По всей базе в горизонт попадают четыре продления: 0,95 + 2,34 + 5,47 + 8,27 = 17,03 €.» |
| Показать метрику «Выручка под риском 5,74 €» | «Из них под риском 0,32 + 0,77 + 1,57 + 3,08 = 5,74 €.» |
| Показать «Исторические пополнения 22 240,73 €» | «Это справочная история и баланс клиентов. Мы их не складываем с прогнозом и не называем потерями.» |

Слайд: **06 «Риск и деньги — разные величины»**.

### Шаг 4. Изменить коэффициент — 50 сек

| Действие | Что говорите |
|---|---|
| Открыть `/settings` | «Проверим гипотезу. Усилим фактор «близость даты окончания» — сейчас вес 3.» |
| Сформулировать ожидание **до** изменения | «Ожидаю, что баллы вырастут и клиентов высокого риска станет больше.» |
| Ввести **9** в поле `expiry_proximity` → **«Сохранить»** | «Меняю вес и сохраняю.» |
| Показать «Сумма весов» | «Сумма весов выросла сразу: 15,0 → 21,0. Фактор помечен «изменено».» |
| Ничего не нажимать | «Сводка пересчитывается на бэкенде и подтягивается сама — страницу не перезагружаю.» |
| Показать метрики в шапке настроек | «Клиентов высокого риска: 2 → 3. Среднего: 4 → 3. Выручка под риском: 5,74 → 7,48 €.» |

**Проверено на стенде (Playwright, без перезагрузки):** сразу после «Сохранить» сумма
весов меняется 15,0 → 21,0, а карточки сводки (клиенты высокого/среднего риска, выручка
под риском) обновляются на месте: 2 → 3, 4 → 3, 5,74 → 7,48 €. URL не меняется, страница
остаётся открытой. Расчёт выполняет сервер; интерфейс сам перечитывает сводку, ручной
перезагрузки не требуется.

Слайд: **07 «Меняем вес — результат пересчитывается»**, левая половина.

### Шаг 5. Доказать, что результат изменился — 40 сек

| Действие | Что говорите |
|---|---|
| Открыть `/customers/10` | «Тот же клиент: балл 73,3 → 81,0.» |
| Показать блок факторов | «Сумма весов выросла с 15,0 до 21,0, вклад фактора — с 3,0 до 9,0. Отсюда 100 × 17,0 / 21,0 = 81,0.» |
| Вернуться в `/settings` → **«Значения по умолчанию»** | «Настройка сохраняется на сервере, поэтому возвращаем исходные значения — балл снова 73,3.» |
| Открыть `/customers` | «И клиент снова на верхней строке — порядок списка тоже пересчитался.» |

Слайд: **07**, правая половина.

**Важно:** пересчёт автоматический. Отдельной кнопки «Пересчитать» в продукте нет —
бэкенд пересчитывает аналитику при сохранении настроек. Не искать эту кнопку на защите.

### Шаг 6. Бизнес-вывод — 25 сек

«Что это даёт команде Aéza: приоритизированный список вместо ручного просмотра,
объяснение вместо непрозрачного числа, денежную оценку отдельно от баланса и
возможность проверить гипотезу за десять секунд. Мы не обещаем автоматического
удержания — продукт помогает решить, с кого начать.»

Слайд: **08 «Команда видит, с кого начать»**.

## Что делать, если что-то сломалось

| Ситуация | Решение |
|---|---|
| Балл #10 не 73,3 | Настройки изменились. `/settings` → «Значения по умолчанию». Если не помогло — данные переимпортированы, используйте слайды 04–07 как источник чисел и говорите «на момент снятия снимка». |
| Дата в шапке не 19.10.2026 15:00 UTC | Снимок перезалит. Числа на слайдах больше не совпадут с экраном. Показывайте слайды, а не интерфейс, и скажите об этом прямо. |
| Интерфейс не отвечает | Переключитесь на резервное окно B. Если и оно молчит — проведите демонстрацию по слайдам 04–07: там те же экраны и те же числа. |
| Вопрос «какая точность модели?» | «Не измерена и не заявлена: в снимке нет истории уходов, обучать и валидировать классификатор не на чем. Модель rule-based и прозрачна.» |
| Вопрос «это макет?» | «Нет. Запущенное приложение: FastAPI + Postgres + React на снимке из комплекта кейса. Скриншоты на слайдах сделаны из него.» |
| Вопрос «что на 10 000 клиентов?» | «Список пагинируется, фильтры и сортировка выполняются в SQL. Нагрузочное тестирование мы не проводили — говорим честно.» |
