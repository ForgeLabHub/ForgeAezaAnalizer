# Концепция Telegram-бота Aéza Analyzer

Рабочая спецификация для дальнейшей разработки. Описывает клиентский Telegram-бот, Mini App, уведомления и переписку с поддержкой в рамках демонстрационного кейса.

## Цель и формат

Бот даёт пользователю сервиса доступ к собственным данным и канал связи с поддержкой. Рекомендуемый формат — Telegram-бот для входа, уведомлений и сообщений плюс Mini App на существующем React-интерфейсе для просмотра баланса и услуг.

В рамках кейса демонстрационная PostgreSQL-база на 40 пользователей считается базой портала. Обновление данных предполагается примерно раз в час. Отдельная интеграция с реальной базой портала не входит в текущий концепт.

## Зафиксированные требования

- Вход выполняется по email с подтверждением одноразовым кодом.
- Если email не найден в базе, код не отправляется.
- Email должен однозначно соответствовать аккаунту. Дубликаты email считаются проблемой данных; бот не должен выбирать запись наугад.
- После подтверждения Telegram связывается с устойчивым ID аккаунта, а не только с email.
- Клиент видит баланс, список услуг, статус каждой услуги и индикатор автопродления.
- Индикатор автопродления только для чтения. Управление настройкой остаётся вне бота.
- Клиент может написать в поддержку в Telegram. Аналитик отвечает из веб-панели; ответ приходит клиенту в бот.
- Автоматические уведомления отправляются за 7 и 3 дня до ожидаемого списания по услуге с включённым автопродлением.
- Дата обновления данных и ссылка на портал в клиентском интерфейсе не показываются.
- Внутренние оценки риска, причины риска и рекомендации аналитика клиенту не показываются.

## Данные и правила

Для клиентского экрана используются поля аккаунта `email` и `balance`, а также поля услуги `status`, `autoProlong`, `expiresAt` и `price`.

Рабочее толкование `expiresAt` по условиям кейса:

- при `autoProlong=true` это ожидаемое время следующего списания;
- при `autoProlong=false` это время окончания услуги, поэтому уведомление именно о списании не отправляется.

Перед запуском расписания толкование `expiresAt` следует сверить с тестовыми записями демонстрационной базы. Время расчёта risk-engine для расписания не использовать: уведомления привязаны к `expiresAt` и текущему времени.

В первой версии напоминания создаются только для услуг со статусом `active` и включённым автопродлением. Статусы `suspended` и `prolong_wait` требуют отдельного подтверждения бизнес-смысла; `deleted` и `blocked` не уведомляются как будущие списания.

Деньги внутри Analyzer представлены в целых евроцентах и отображаются в евро. Поле `transactions.amount` не является денежной суммой и для текста уведомлений не используется. При отсутствующем балансе показывается отсутствие данных, а не ноль.

## Пользовательские сценарии

### Привязка Telegram

1. Пользователь запускает бота и вводит email.
2. Backend ищет email без учёта регистра в демонстрационной базе.
3. Если совпадений нет, код не отправляется и бот сообщает, что аккаунт не найден.
4. Если найден ровно один аккаунт, backend запрашивает у почтового сервиса отправку кода.
5. Пользователь вводит код в боте. После успешной проверки Telegram ID связывается с ID аккаунта.
6. Пользователь даёт согласие на уведомления и открывает Mini App.

Код должен иметь ограниченный срок действия, ограничение числа попыток и повторной отправки. Код хранится в защищённом виде и не попадает в журналы. Повторная привязка требует нового подтверждения email.

### Просмотр данных

Mini App показывает баланс и услуги привязанного аккаунта: название, статус, цену, дату окончания или ожидаемого продления и состояние автопродления. Никаких действий, меняющих состояние услуги, в Mini App нет.

### Уведомления

Для каждой подходящей услуги планируются два уведомления: в момент `expiresAt - 7 дней` и `expiresAt - 3 дня`. Текст обозначает дату и сумму как ожидаемые, не как подтверждённую транзакцию. Если `autoProlong` отключили или `expiresAt` изменился, неотправленные уведомления пересчитываются.

Периодический обработчик сверяет наступившие сроки с актуальными данными. Уведомление отправляется не более одного раза для сочетания аккаунта, услуги, `expiresAt` и интервала. Рекомендуемый интервал проверки — несколько минут; задержка обновления самой базы может составлять около часа.

### Поддержка

Сообщение клиента создаёт или продолжает диалог, связанный с аккаунтом. В панели аналитика видит историю и может ответить. Ответ сохраняется и отправляется пользователю через Telegram. Ошибки Telegram-доставки фиксируются, чтобы сообщение не считалось доставленным без подтверждения.

## Предлагаемая архитектура

- **Telegram Bot API** принимает команды и сообщения клиента, отправляет ответы и уведомления.
- **Mini App** использует существующий React frontend; Telegram Web App init data проверяется backend на сервере.
- **FastAPI backend** выполняет поиск аккаунта, проверку одноразового кода и выдаёт клиенту только данные связанного аккаунта. Клиентская авторизация отделена от существующего входа аналитиков.
- **Почтовый сервис напарника** отправляет код подтверждения. Контракт API сервиса нужно согласовать до реализации; в диалоге имя указано как `smpt.bz`.
- **PostgreSQL Analyzer** хранит Telegram-привязки, согласия, коды подтверждения, диалоги, сообщения и очередь уведомлений.
- **Фоновый обработчик** рассчитывает сроки уведомлений и отправляет очередь. Для демонстрационного MVP достаточно очереди в PostgreSQL с уникальным ключом доставки; Redis/Celery пока не закладываются.
- **Веб-панель** расширяется разделом поддержки для списка диалогов, истории сообщений и отправки ответа.

Текущие API клиентов рассчитаны на авторизованных аналитиков. Для бота нужны отдельные клиентские API с проверкой Telegram-привязки и ограничением выборки одним аккаунтом.

## План разработки

1. **Проверить демонстрационные данные.** Подтвердить 40 аккаунтов, уникальность email, наличие нужных полей и соответствие `expiresAt` ожидаемому списанию при включённом автопродлении.
2. **Согласовать почтовый контракт.** Определить API отправки, шаблон кода и формат ошибок сервиса напарника.
3. **Сделать вход и привязку.** Добавить OTP-поток, Telegram ID, согласие на уведомления, защиту от повторной отправки и клиентскую авторизацию.
4. **Сделать клиентский экран.** Добавить Mini App и API баланса/услуг с проверкой привязанного аккаунта.
5. **Сделать поддержку.** Добавить хранение диалогов, сообщения Telegram и раздел входящих/ответов в веб-панели.
6. **Сделать уведомления.** Добавить расписание, очередь PostgreSQL, дедупликацию, повтор доставки при временной ошибке и отмену устаревших запланированных сообщений.
7. **Проверить демонстрационный сценарий.** Пройти регистрацию, неверный/истёкший код, email без аккаунта, просмотр нескольких услуг, диалог в обе стороны, отключённое автопродление, смену `expiresAt`, повторы и недоступность Telegram.

## Границы первой версии

В первую версию не входят изменение автопродления, ссылка на портал, дата последнего обновления, клиентские оценки риска, уведомления о фактически прошедшем платеже и поддержка нескольких email на один аккаунт.

Новые внешние интеграции: Telegram Bot API и почтовый сервис для OTP. Конкретная Python-библиотека для Telegram пока не выбрана.

## Нюансы

- Часовой пояс по мск
- Можно привязать несколько Telegram-аккаунтов к одному клиентскому аккаунту.
- Нужно позже отправлять отдельное напоминание об окончании услуги при выключенном автопродлении.
- Поведение для `suspended: отправляем о платеже через 3 дня`, и `prolong_wait`: в течении 5 дней, каждый день приходит уведомление о необходимости оплаты, или услуга будет 
- Срок хранения истории поддержки - 30 дней. Аналитик имеет доступ к диалогу в любой момент, и может его начать по своему усмотрению.
