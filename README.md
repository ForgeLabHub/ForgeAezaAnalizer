# Aéza Analyzer

Аналитика клиентских данных Aéza для хакатона **UMIRHack 2026, кейс №2**:
выявление риска оттока, объяснение причин каждой оценки и расчёт выручки под
риском на **официальном датасете организатора** (10 аккаунтов, 30 услуг,
100 транзакций). Данные синтетические: их сгенерировал организатор
(`dataset/generate.py`), это снимок состояния, а не история событий.

Продукт отвечает на три вопроса: **кому** нужно внимание, **почему** возник
риск и **сколько денег** под угрозой. Балл риска — прозрачная взвешенная
rule-based оценка, а не откалиброванная вероятность оттока: в датасете нет
исторических исходов, поэтому метрик accuracy/precision/recall здесь не может
быть, и нигде в интерфейсе они не заявляются.

Встроенный **AI-аналитик** (локальная модель через Ollama + локальный RAG)
объясняет оценки Risk Engine человеческим языком. Числа он не считает —
он берёт их из backend и ссылается на источники. Подробности:
[docs/AI_ANALYST.md](docs/AI_ANALYST.md).

## Канонический продукт

**Единственный поддерживаемый runtime — часть B**: FastAPI (`backend/app/`) плюс
React + TypeScript (`frontend/`). Точка входа одна — корневой `main.py`
(`uvicorn main:app`); её же использует `backend/Dockerfile`. Ядро оркестрации
версий и атомарной публикации расчётов находится в `core.py`. Запуск одной
командой:

```bash
cp .env.example .env        # обязательно задайте POSTGRES_PASSWORD —
                            # без него Compose не стартует
docker compose up --build   # web :8080, api :8000
```

При старте подключается реальный аналитический модуль
(`AEZA_ANALYTICS_FACTORY=backend.app.domain.module:create`, это значение задано в
`.env.example` и `docker-compose.yml`) и загружается официальный датасет 10/30/100
через штатный импортёр. Если переменная пуста, приложение стартует с заглушкой,
отвечающей `503`, и не выдаёт фиктивных расчётов. Контракт подключения внешнего модуля
описан в [docs/PROJECT_GUIDE.md](docs/PROJECT_GUIDE.md).

> в канонический сценарий, не импортируются частью B и сохранены как история. Не

## 3. Модель риска

```
risk_score = 100 × Σ(weightᵢ × featureᵢ) / Σ(weightᵢ)
```

Это **объяснимая взвешенная модель признаков, а не обученная ML-модель**:
в датасете 10 аккаунтов и 30 услуг — недостаточно размеченных данных об
оттоке, чтобы обучать и валидировать статистическую модель.

Факторы (все нормализуются в диапазон 0–1, больше = выше риск):

| Ключ | Вес по умолчанию | Смысл |
|------|------------------|-------|
| `expiry_proximity` | 1.0 | услуга близко к окончанию (в пределах горизонта) |
| `autoprolong_off` | 0.8 | автопродление отключено |
| `insufficient_balance` | 1.0 | доступный баланс меньше цены услуги |
| `failed_renewals` | 0.6 | были неуспешные продления |
| `status_risk` | 0.9 | статус услуги (blocked/suspended/prolong_wait) |

Уровни риска: **низкий 0–34, средний 35–64, высокий 65–100**.

Важные свойства модели:

- **Неизвестное ≠ нулевой риск.** Если данных для фактора нет (`None`),
  фактор исключается и из числителя, и из знаменателя, а `confidence`
  снижается. Так отсутствие данных не «успокаивает» модель.
- **Завершённые события отделены от прогноза.** Услуги со статусом `deleted`
  исключены из прогноза будущего оттока; клиенты только с такими услугами
  получают уровень `churned` (уже ушли), а не «низкий риск».
- **Риск клиента и деньги считаются отдельно.** `risk_score` клиента — по
  худшей «живой» услуге; `revenue_at_risk` — независимая денежная оценка.
- Веса настраиваются через UI/API и валидируются (неизвестные ключи,
  отрицательные значения и «все нули» отклоняются).

## 4. Выручка под риском

```
revenue_at_risk = eligible_renewal_amount × risk_score / 100
```

- учитываются только **будущие** продления в пределах горизонта
  (`reference_at ≤ expiresAt ≤ reference_at + horizon`);
- `deleted`-услуги и уже истёкшие продления не считаются;
- каждое продление учитывается **один раз**;
- **баланс и исторические пополнения не входят** в выручку под риском.

`reference_at` — момент снимка данных. Определяется из самих данных (максимум
`createdAt`/`performedAt`), поэтому расчёты воспроизводимы и не зависят от
времени запуска.

## 5. Денежные единицы

Правило кейса: **100 исходных единиц = €1**. В README организатора указано, что
денежные поля аккаунта и `price` хранятся в **евроцентах**.

- Каноническое внутреннее представление — целые **евроценты** (без float).
- Евро вычисляются один раз на границе API/UI (`*_eur` рядом с `*_cents`).
- Двойной конвертации нет; смешения баланса, бонусов, пополнений, цены
  услуги и суммы транзакции нет — у каждого поля своя семантика.

## 7. Идемпотентность и атомарность импорта

- Импорт пишет весь датасет в **одной транзакции**: ошибка откатывает всё,
  частично обновлённой базы не остаётся.
- Повторный импорт **заменяет** таблицы целиком → дубликатов нет.
- Если хотя бы одна строка не прошла валидацию, импорт по умолчанию
  **прерывается** и перечисляет отклонённые строки (`--lenient` сохранит
  валидные строки и отчёт об отклонённых).
- Каждый запуск пишется в `import_runs` (sha256 архива, количества, статус).

## 8. Ограничения

- Данные **синтетические** (сгенерированы организатором); это снимок состояния,
  а не полная история. Транзакции содержат только типы `order` и `prolong`,
  поэтому полной истории пополнений нет.
- Балансы не выводятся из транзакций — они заданы независимо.
- Модель риска — эвристическая и объяснимая, **не** обученная ML-модель.
- Хранилище — SQLite (встроенное); при необходимости заменяется через
  `AEZA_DATABASE_URL`.
- `favicon.ico` не отдаётся (безвредный 404 в консоли).

[`docs/PROVENANCE_AUDIT.md`](docs/PROVENANCE_AUDIT.md).

# Часть B — FastAPI + React (канонический продукт)

Единственный поддерживаемый runtime кейса: FastAPI-бэкенд с PostgreSQL (или
SQLite) и React + TypeScript SPA под nginx. Собственный скоринг, импорт снимка и
фронтенд. Ниже — полный рабочий сценарий.

Система анализа клиентской базы Aéza: выявление клиентов и услуг с повышенным риском
оттока, объяснение причин оценки, рекомендации по удержанию и оценка выручки под риском.

Кейс #2, UMIRHack 2026. Источник данных — синтетический снимок
(`accounts`, `services`, `transactions`): 10 аккаунтов, 30 услуг, 100 транзакций.

---

## Что делает система

1. **Считает риск оттока** для каждой услуги и агрегирует его до клиента прозрачной
   взвешенной формулой (не «чёрный ящик»).
2. **Объясняет оценку**: каждая услуга возвращает список факторов с их значением,
   весом, вкладом и текстовым обоснованием.
3. **Разделяет три разные вещи**, которые легко перепутать:
   - текущее состояние (`active`, `suspended`, `prolong_wait`);
   - уже состоявшееся событие (`deleted`, `blocked`) — не прогнозируется;
   - прогноз риска по услугам, которые ещё могут быть продлены.
4. **Оценивает выручку под риском** отдельно от баланса клиента и исторических
   пополнений.
5. **Даёт рекомендации по удержанию**, привязанные к реальным сигналам в данных.
6. **Позволяет менять веса модели и горизонт прогноза** — настройки сохраняются на
   сервере и немедленно меняют результаты.
7. **Импортирует снимок данных** через API с полной валидацией и атомарным
   применением.

### Честные ограничения

- **Модель не откалибрована.** В данных нет исторических исходов оттока (кто и когда
  ушёл), поэтому обучить и провалидировать ML-модель невозможно. Используется
  объяснимый rule-based скоринг. Балл риска — **не вероятность в процентах**.
- **Динамики нет.** Снимок описывает одно состояние; вместо выдуманного графика
  тренда интерфейс показывает актуальное распределение и прямо сообщает об отсутствии
  истории.
- **Данные синтетические.** Балансы не вычисляются из транзакций, `amount`
  генерируется независимо от `price`, полной истории пополнений нет.

## Запуск через Docker Compose

Поднимает три сервиса: PostgreSQL, API и веб-интерфейс (nginx).

```bash
cp .env.example .env      # обязательно: POSTGRES_PASSWORD
docker compose up --build
```

Секретов по умолчанию нет: `docker compose up` **не стартует**, пока не задан
`POSTGRES_PASSWORD`. Это сделано намеренно — общее окружение не должно
подниматься с демонстрационным паролем. `AEZA_CORS_ORIGINS` по умолчанию
ограничен `http://localhost:8080`.

| Сервис | Адрес | Назначение |
| --- | --- | --- |
| web | <http://localhost:8080> | Интерфейс (nginx раздаёт SPA и проксирует API) |
| api | <http://localhost:8000> | REST API и `/metrics` |
| db | внутренний | PostgreSQL 16 |

Данные и авторизация хранятся в именованных томах Docker (`pg_data`, `auth_data`),
поэтому запуск не зависит от файлов в рабочем каталоге и переживает перезапуск:

- при первом старте API создаёт схему и загружает **официальный датасет 10/30/100**
  из `dataset/data.json` через штатный импортёр (`AEZA_SEED_DEMO_DATA=1`);
- SQLite-файл авторизации создаётся приложением в томе `auth_data` под
  непривилегированным пользователем — каталог `/app/db` не монтируется с хоста.

## Загрузка данных вручную

Compose при первом старте загружает официальный датасет `dataset/data.json`
(10/30/100) через штатный импортёр. Данные PostgreSQL и SQLite-база авторизации
хранятся в именованных томах Docker (`pg_data`, `auth_data`). Чтобы импортировать
другой снимок:

```bash
cd backend
python scripts/load_snapshot.py ../dataset/data.json
```

Тот же результат доступен через API:

```bash
curl -X PUT http://127.0.0.1:8000/api/v1/source/snapshot \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @dataset/data.json
```

Импорт валидируется целиком **до** записи; при ошибке предыдущий набор остаётся
неизменным. Ответ содержит отчёт: принятые, отклонённые и дублирующиеся записи.

Подробности: [`docs/PROJECT_GUIDE.md`](docs/PROJECT_GUIDE.md).

## AI Analyst (локальная LLM)

Модуль `backend/app/ai/` объясняет уже посчитанные оценки Risk Engine через

становится видно и аналитику, и AI-аналитику. Записывает действие только человек
через API — у AI-модуля маршрута записи нет.

## Безопасность

- Пароли хранятся как PBKDF2-HMAC-SHA256 с индивидуальной солью; открытый пароль не
  сохраняется.
- Токены выдаёт автономный модуль `backend/auth/`: RS256, ключ в томе `auth_data`.
- Пароль и ключ не вшиты в код и не лежат в репозитории.
- В production задайте HTTPS-`AUTH_ISSUER` и `AUTH_COOKIE_SECURE=true`; модуль
  отказывается стартовать с небезопасной комбинацией.
- В логи и метрики не попадают email, идентификаторы клиентов и иные персональные
  данные: метрики агрегированы, меток с высокой кардинальностью нет.

# Часть C (архив) — модуль авторизации (`backend/auth/`)

Автономный модуль: логин и пароль в SQLite, JWT access token, HttpOnly cookie
серверной сессии, RS256/JWKS и OIDC-провайдер для одного доверенного сайта.
Не зависит от частей A и B; фронтенд в этот модуль не входит.

Модуль проверяет логин и пароль в SQLite, выдаёт JWT access token и устанавливает HttpOnly cookie серверной сессии. Повторные запросы используют сессию; пароль не сохраняется в кеше. Модуль выступает OIDC-провайдером для одного доверенного сайта.

Добавлены зависимости **PyJWT и cryptography** для RS256/JWKS. SQLite, scrypt и кеш используют стандартную библиотеку Python. Фронтенд в этот модуль не входит.

## Запуск

Нужны Docker и Docker Compose. Сначала создайте локальный файл настроек и задайте собственные секрет и пароль администратора:

```powershell
Copy-Item .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Для локального Compose оставьте `AUTH_ISSUER=http://localhost:8080` и `AUTH_COOKIE_SECURE=false`; для production задайте HTTPS-домен и `AUTH_COOKIE_SECURE=true`. Затем запустите стек:

```powershell
docker compose up -d --build
```

Интерфейс: <http://localhost:8080>. API: <http://localhost:8000>. Swagger: <http://localhost:8000/api/v1/docs>. Учётные записи создаёт модуль авторизации: `docker compose exec api python -m backend.users create <login>`.

Compose запускает PostgreSQL, API и frontend. Seed загружается при первой инициализации пустого тома PostgreSQL. Данные сохраняются между перезапусками. `docker compose down` останавливает сервисы, не удаляя тома.

## Что считает приложение

- Риск оценивается по открытым услугам и объясняется факторами модели. `deleted` и `blocked` отражают уже известное состояние и не включаются в прогноз будущего оттока.
- Риск клиента определяется максимальным score среди прогнозируемых услуг.
- Выручка под риском считается отдельно от риска. Цена услуги не повышает score.
- Денежные значения хранятся в целых евроцентах; конвертация в евро выполняется на границе отображения.
- Опорное время по умолчанию закреплено на `2026-10-19T15:00:00Z`, чтобы расчёты воспроизводились.

# Часть C — быстрый запуск модуля авторизации (`backend/auth/`)

Модуль автономен и работает на своей SQLite-базе и своём ключе RS256.

Для production до запуска задайте `AUTH_ISSUER` и `AUTH_FRONTEND_LOGIN_URL` на
HTTPS-домен приложения, `AUTH_COOKIE_SECURE=true` и точный `AEZA_CORS_ORIGINS`.

```powershell
Copy-Item .env.example .env
docker compose up -d --build
docker compose exec api python -m backend.users create analyst@example.com
```

Команда создания пользователя запросит пароль дважды. Пользователи хранятся в
`db/auth.sqlite3` в постоянном Docker volume (`auth_data`); ключ RS256
сохраняется рядом. Приложение не заводит администратора при старте само.
