# Data and risk model

Audience: developers and reviewers of the `backend/app/` product.
Sources of truth: the code in `backend/app/domain/`, the organiser dataset
`dataset/data.json`, and `ТЗ.pdf`. Every figure below was reproduced by running
the engine; see `docs/audits/calculation-audit.md` for the raw transcript.

## 1. Data shape

The snapshot has three arrays, matching the organiser schema 1:1.

| Array | Count on the official set | Key fields |
| --- | --- | --- |
| `accounts` | 10 | `id`, `email`, `balance`, `withdrawBalance`, `bonusBalance`, `bonusState`, `totalReplenished` |
| `services` | 30 | `id`, `name`, `ownerId`, `paymentTerm`, `autoProlong`, `createdAt`, `expiresAt`, `status`, `price` |
| `transactions` | 100 | `id`, `serviceId`, `status`, `type`, `amount`, `createdAt`, `performedAt` |

The data is **synthetic**, generated by `dataset/generate.py`. It is a snapshot of
one moment, not an event history: the organiser's own README says status changes
and deletion dates are absent.

## 2. Units — money is integer eurocents

- Every monetary value is an **integer number of eurocents**; `100` cents = `€1`.
- Euros appear only as `*_eur` strings added at the API boundary by
  `backend/app/domain/money.py`.
- Conversion happens **once**. `money.py` uses `Decimal` with `ROUND_HALF_UP`.
- `transactions.amount` is **not money**. The organiser states it is generated
  independently of `price`; it is never used in revenue.

What each money figure means:

| Field | Meaning | Unit | Used for |
| --- | --- | --- | --- |
| `balance` | main account balance in real money | cents | sufficiency check for renewal |
| `withdrawBalance` | balance withdrawable to real money / platform, earned via referrals | cents | **not** used in the current model (see §5) |
| `bonusBalance` | promo balance, spendable only when `bonusState == "unlocked"` | cents | sufficiency check, conditionally |
| `totalReplenished` | lifetime real top-ups | cents | display / sorting only, never in the score |
| `price` | service cost | cents | revenue exposure, never the score |
| `revenueAtRisk` | weighted expected loss inside the horizon | cents | the money estimate |

## 3. Risk score — a transparent weighted rule, not a probability

`risk_score = 100 × Σ(wᵢ · fᵢ) / Σ(wᵢ)`, summing **only the applicable** factors.
Each `fᵢ ∈ [0, 1]`; missing inputs are `None` and are dropped from both numerator
and denominator, and `confidence` records the coverage.

**A missing signal never lowers risk.** An unknown factor is excluded, not
treated as zero, so thin data produces a lower `confidence` rather than a falsely
low score.

Default weights (`backend/app/domain/risk.py`, `DEFAULT_WEIGHTS`):

| Factor | Key | Weight | Reads |
| --- | --- | --- | --- |
| Expiry proximity | `expiry_proximity` | 3.0 | `expiresAt` vs the horizon |
| Auto-prolong disabled | `auto_prolong_disabled` | 2.0 | `autoProlong == false` |
| Insufficient balance | `insufficient_balance` | 2.0 | `balance` (+ bonus when unlocked) vs `price` |
| Prolong wait | `prolong_wait_status` | 2.5 | `status == prolong_wait` |
| Renewal failure rate | `renewal_failure_rate` | 2.5 | failed `prolong` transactions / attempts |
| Suspended | `suspended_status` | 1.0 | `status == suspended` |
| Failed renewals (count) | `failed_renewals` | **0.0** | deprecated: the signal is already in `renewal_failure_rate`, so a non-zero weight would double-count |

Thresholds (`level_for`): **low 0–34**, **medium 35–64**, **high 65–100**.
Fractional scores in the gaps (e.g. `34.9`) stay in the lower band.

Customer risk is the **maximum over forecastable services**, not an average:
one badly at-risk service should not be diluted by healthy ones.

### States kept apart

- **Current** — `active`, `suspended`, `prolong_wait`.
- **Concluded** — `deleted`, `blocked`. Already-churned history, excluded from
  forward scoring. An account whose only services are concluded gets
  `not_applicable`, not a false `low`.
- **Forecast** — the risk on services that can still be renewed.

`price` never feeds the score: cost is exposure, not likelihood.

## 4. Revenue at risk

`revenue_at_risk = price × score/100`, computed **only** for open services with a
positive price whose `expiresAt` falls inside the horizon, counting each renewal
once. It is a weighted expected loss, not the balance and not the sum of prices.

Time horizons: `7 / 30 / 90` days are exposed (`revenue.HORIZONS`); the working
horizon defaults to **30** days. `overdue` exposure (already past `expiresAt`) is
reported separately from future renewals so the two are never added together.

## 5. Deliberate exclusions

- `withdrawBalance` is **not** used for sufficiency; the model uses `balance`.
  On the shipped dataset the two never disagree (0 disagreeing pairs across every
  open service with `price > 0` at horizons 30/60/90/180/365), so the choice is
  invisible here. It would matter on a dataset with a large price against a
  drained `withdrawBalance`.
- Bonus balance counts toward sufficiency **only** when `bonusState ==
  "unlocked"`. An unknown bonus state is treated as unavailable.
- `amount` is never money.
- No synthetic history is created. The snapshot has no event history, so no
  trend line or "predicted churn over time" is fabricated.

## 6. Reference time

`AEZA_AS_OF` defaults to `2026-10-19T15:00:00+00:00`, the dataset's documented
moment, so "days until expiry" and every score are reproducible. `now` switches
to wall-clock time for a live view. Change it deliberately, not incidentally.

## 7. Reproducing the control values

```bash
PYTHONPATH=.:backend python - <<'PY'
import json, datetime as dt
from core import State
from backend.app.domain.module import create
state = State(generation=1, source_version=1, model_version=1,
    source=json.load(open("dataset/data.json")),
    settings={"horizonDays": 30,
        "weights": {"expiry_proximity": 3.0, "auto_prolong_disabled": 2.0,
                    "insufficient_balance": 2.0, "prolong_wait_status": 2.5,
                    "failed_renewals": 0.0, "suspended_status": 1.0,
                    "renewal_failure_rate": 2.5},
        "lowMax": 34, "mediumMax": 64, "failedRenewalWindowDays": 90},
    as_of=dt.datetime(2026, 10, 19, 15, 0, tzinfo=dt.timezone.utc))
result = create().calculate(state)
print(result.summary["revenue"])              # revenueAtRiskEur == "5.80"
print([c["riskScore"] for c in result.customers])  # customer 10 -> 71.4
PY
```

Expected: `revenueAtRiskEur` **5.80**, `upcomingRenewalsEur` **17.03**,
categories **3 high / 3 medium / 4 not_applicable**, and customer #10 score
**71.4**. Changing `expiry_proximity` to `9.0` moves the score to **81.8** and
revenue to **7.72 €**.

## 8. How to read the score honestly

- It is **not** a calibrated probability. The snapshot has no churn labels, so no
  statistical model can be trained or validated. `summary.model.calibrated` is
  `false` and `summary.model.type` is `rule_based_weighted`.
- A high score means "this customer matches several known attention signals",
  not "this customer has an N% chance of leaving".
- `confidence` reflects how many inputs were available; low confidence means
  "we know little", not "risk is low".
