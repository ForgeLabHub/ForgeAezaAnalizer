# Структура исходных данных

Источник: комплект кейса UMIRHack 2026, каталог [`dataset/`](../dataset/).
Файл `dataset/data.json` — снимок PostgreSQL-базы Aéza. Комплект также содержит
SQL-схему, сид-скрипт, генератор и его собственный README.

Проверенная сверка: файлы в `dataset/` побайтово совпадают с комплектом из репозитория
кейса (см. `docs/readiness.md`). Данные синтетические.

---

## Объём

| Сущность | Записей |
| --- | --- |
| `accounts` | 10 |
| `services` | 30 |
| `transactions` | 100 |

В `data.json` это один объект с тремя массивами:

```json
{ "accounts": [...], "services": [...], "transactions": [...] }
```

Именно этот формат принимает `PUT /api/v1/source/snapshot`.

## Схема

### `accounts`

| Поле | Тип | Примечание |
| --- | --- | --- |
| `id` | int | Первичный ключ, с 1 |
| `email` | str | Уникален с учётом регистра, вид `user-0001@example.test` |
| `balance` | int | Евроценты |
| `withdrawBalance` | int | Евроценты; `withdrawBalance <= balance` |
| `totalReplenished` | int | Евроценты; суммарно пополнено |
| `bonusBalance` | int | Евроценты |
| `bonusState` | str | `locked` / `unlocked` |

### `services`

| Поле | Тип | Примечание |
| --- | --- | --- |
| `id` | int | Первичный ключ |
| `name` | str | Латиница, цифры, дефис (например `service-0001`) |
| `ownerId` | int | → `accounts.id` |
| `paymentTerm` | str | `hour`, `week`, `month`, `quarter_year`, `half_year`, `year` |
| `autoProlong` | bool | Автопродление |
| `createdAt` | str | UTC, ISO-8601 с миллисекундами и `Z` |
| `expiresAt` | str | UTC; `expiresAt >= createdAt` |
| `status` | str | `active`, `suspended`, `prolong_wait`, `deleted`, `blocked` |
| `price` | int | Евроценты, стоимость одного периода |

### `transactions`

| Поле | Тип | Примечание |
| --- | --- | --- |
| `id` | int | Первичный ключ |
| `amount` | int | 0…1000 включительно (предел из задания) |
| `status` | str | `performed`, `not_performed` |
| `performedAt` | str \| null | `null` только при `not_performed` |
| `createdAt` | str | UTC |
| `type` | str | `prolong`, `order` |
| `serviceId` | int | → `services.id` |

Связи: `services.ownerId → accounts.id`, `transactions.serviceId → services.id`.

## Денежные единицы

Все денежные поля — **целые евроценты**, без плавающей точки. В условиях кейса задано
преобразование: 100 единиц = €1.

К нему относятся:

- `accounts.balance`, `withdrawBalance`, `totalReplenished`, `bonusBalance`;
- `services.price`.

Это подтверждено README комплекта: *«Денежные поля аккаунта и `price` —
неотрицательные целые значения в евроцентах, без floating point. `totalReplenished`
также трактуется как евроценты.»*

Преобразование выполняется **один раз**, в единственном месте — `app/domain/money.py`
(`cents_to_eur`). Хранение остаётся в центах (целые числа), в евро значения
переводятся только для отображения. Повторная конвертация исключена архитектурно:
внутри системы не существует «уже переведённых» денежных полей.

### Что с чем не смешивается

| Величина | Источник | Роль |
| --- | --- | --- |
| Баланс | `accounts.balance` | Средство оплаты, не выручка |
| Бонусный баланс | `accounts.bonusBalance` | Справочно |
| Исторические пополнения | `accounts.totalReplenished` | Справочная метрика |
| Стоимость продления | `services.price` | Основа выручки под риском |
| Выручка под риском | Расчёт | Прогнозная экспозиция |

Выручка под риском **не включает** баланс и `totalReplenished`: это разные по смыслу
величины, и складывать их нельзя.

### `transactions.amount` сознательно не используется

README комплекта прямо указывает: `amount` генерируется независимо от `price`, а
балансы не вычисляются из транзакций. Поэтому `amount` **не участвует** ни в скоринге,
ни в расчёте выручки: любое такое использование дало бы числа, не связанные с реальной
экономикой услуги. Поле сохраняется в базе для полноты и трассируемости.

### Ручная проверка преобразования

| Запись | Исходное значение | Евро |
| --- | --- | --- |
| `accounts[0].balance` | 20379 | 203,79 € |
| `accounts[0].totalReplenished` | 420669 | 4 206,69 € |
| `services[25].price` (id 26) | 547 | 5,47 € |

Те же значения видны в интерфейсе: карточка клиента #10 показывает баланс 203,79 €.

## Качество данных

Проверено скриптами и тестами:

- **Дубликатов нет.** Идентификаторы уникальны в каждой таблице.
- **Внешние ключи целостны.** Каждый `ownerId` и `serviceId` разрешается в
  существующую запись.
- **Диапазон `amount` соблюдён.** Границы 0 и 1000 встречаются в первых двух
  транзакциях.
- **Даты согласованы.** `expiresAt >= createdAt`; при `not_performed` поле
  `performedAt` пустое.
- **Бизнес-инварианты.** `withdrawBalance <= balance` и
  `totalReplenished >= balance` выполняются во всём наборе.

Импорт дополнительно проверяет всё перечисленное и отклоняет набор при нарушении
(см. [`import.md`](import.md)).

### Распределения

| Признак | Распределение |
| --- | --- |
| `services.status` | по 6 записей на каждый из 5 статусов |
| `services.autoProlong` | `false` — 14, `true` — 16 |
| `services.paymentTerm` | по 5 записей на каждый из 6 периодов |
| `services.price` | 72…960 центов |
| `transactions.status` | `performed` — 67, `not_performed` — 33 |
| `transactions.type` | `prolong` — 70, `order` — 30 |
| `accounts.bonusState` | `locked` / `unlocked` |

Распределение статусов намеренно равномерное: набор предназначен для проверки
обработки всех состояний, а не для имитации реальной клиентской базы.

## Опорный момент времени

Комплект фиксирует опорную дату **`2026-10-19T15:00:00.000Z`** и прямо указывает, что
состояния услуг не обновляются со временем. Это снимок одного момента.

Отсюда поведение приложения:

- `AEZA_AS_OF` по умолчанию равен этой дате, поэтому «дней до окончания» и все баллы
  воспроизводимы;
- значение `now` включает живой режим по стенным часам;
- любое другое значение ISO-8601 сдвигает опорный момент.

Без фиксации опорного момента услуги со статусом `prolong_wait` и `deleted` выглядели
бы «просроченными на годы», что искажало бы демонстрацию. Значение по умолчанию
соответствует семантике снимка.

### Наблюдение по данным

Относительно опорного момента:

- все 6 `active` услуг истекают в будущем (от 0 до 365 дней);
- все 6 `deleted` услуг истекли задолго до опорного момента (35…400 дней назад) —
  это согласуется со статусом «удалена»;
- все 6 `prolong_wait` услуг также истекли (35…400 дней назад): услуга ждёт
  продления, срок оплаченного периода уже закончился;
- `suspended` и `blocked` распределены по обе стороны от опорного момента.

Это наблюдение, а не предположение: оно получено прямым вычислением по `expiresAt`.

## Пригодность для прогнозирования

| Данные | Пригодны для |
| --- | --- |
| `services.status`, `autoProlong`, `expiresAt`, `price` | Скоринг риска, выручка под риском |
| `transactions` (тип, статус) | Факторы истории продлений |
| `accounts.balance` | Фактор достаточности средств |
| `accounts.totalReplenished`, `bonusBalance` | Только описательная аналитика |

Чего в данных **нет**:

- исторических исходов оттока (кто ушёл и когда) — поэтому модель нельзя обучить и
  откалибровать;
- событий отмены услуг;
- полной истории пополнений.

Следствие: система использует объяснимый rule-based скоринг и честно сообщает об этом
в интерфейсе и документации. Подробнее — [`model.md`](model.md).
