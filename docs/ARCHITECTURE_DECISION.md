# Архитектурное решение

## Решение

**Основной продукт для демонстрации жюри — реализация B:**
`backend/app/` + `frontend/` (FastAPI + React/TypeScript + Docker Compose).

Она дополняется отдельным сервисом `backend/auth/` (JWT/OIDC), который входит
в тот же стек.

Реализация **A** (`aeza_analyzer/`) **сохраняется** как независимый
инструмент: у неё сильнейший импортёр, документация и тесты, но она не
соответствует обязательным требованиям ТЗ (нет `/metrics`, Docker,
аутентификации и контракта `/api/v1/*`).

## Обоснование

Решение принято по обязательным критериям приёмки из `ТЗ.pdf`, а не по объёму
кода:

| Обязательный критерий ТЗ | A | B |
|---|---|---|
| Контракт `/api/v1/auth|customers|analytics|model|source` | ❌ | ✅ |
| `GET /metrics` в формате Prometheus | ❌ | ✅ |
| Аутентификация защищает панель и API | ❌ | ✅ |
| Docker Compose запускает решение | ❌ | ✅ |
| Swagger `/api/v1/docs` | 🟡 | ✅ |
| Сортировка по ID, email, балансу, пополнениям | 🟡 | ✅ |
| Живое обновление без reload | 🟡 | ✅ |

По ТЗ: «Без выполнения этих условий решение не принимается». B закрывает
обязательные пункты, A — нет. Поэтому основной сценарий строится на B.

## Что делаем с каждой реализацией

| Компонент | Решение | Причина |
|---|---|---|
| `backend/app/` + `frontend/` | **основной продукт** | полное соответствие ТЗ |
| `backend/auth/` | **сервис аутентификации основного продукта** | реализует JWT/OIDC; подключён к стеку |
| `aeza_analyzer/` | **сохранить как независимый инструмент** | ценный импортёр, документация, 52 теста; удалять чужую работу нельзя |
| `tests/test_auth.py`, `tests/test_*.py` | **сохранить** | покрывают A и C |

### Почему не удаляем A

1. **Запрещено протоколом**: нельзя удалять чужие наработки без
   архитектурного обоснования.
2. **A содержит уникальное**: самый строгий безопасный импорт, `import_runs`
   (журнал импорта с sha256), полный набор из 12 документов.
3. **A полезна как референс**: её импортёр и `UTCDateTime` решают реальные
   проблемы, которые в B решены иначе.
4. **Удаление A уже один раз сломало `main`** (`986e67c` оставил тесты без
   модуля).

### Почему не сливаем код A и B

У них **разные формулы риска** (5 факторов против 7), **разные пути API**
(`/api/*` против `/api/v1/*`) и разные модели данных. Механическое слияние
создало бы два конкурирующих источника истины для одних и тех же бизнес-данных
— это прямо запрещено. Консолидация потребовала бы переписывания одного
продукта поверх другого и выходит за рамки безопасного изменения.

## Единый пользовательский сценарий

Один основной сценарий — **B**:

```bash
cp .env.example .env      # задать AEZA_JWT_SECRET и пароль администратора
docker compose up --build
# панель:  http://localhost:8080
# API:     http://localhost:8000/api/v1
# Swagger: http://localhost:8000/api/v1/docs
# метрики: http://localhost:8000/metrics
```

Дополнительный способ (A), без Docker:

```bash
./run.sh        # http://127.0.0.1:8000
```

## Карта миграции (если потребуется единый продукт)

Если команда решит свести всё к одному продукту, порядок такой:

1. Перенести в B безопасный импортёр A (`importer/archive.py` +
   `validation.py`) — он строже текущего.
2. Добавить в B журнал `import_runs` из A для аудита импорта.
3. Выбрать **одну** формулу риска и удалить вторую.
4. Оставить в A только CLI-инструмент импорта, если он нужен отдельно.
5. Удалить дублирующую документацию.

Это отдельная задача; в текущем объёме обе реализации сохранены рабочими.

## Риски решения

| Риск | Оценка | Митигация |
|---|---|---|
| Два продукта в одном репозитории путают жюри | средний | README явно разделяет Часть A и Часть B, указан основной способ запуска |
| Расхождение формул риска | низкий | каждая реализация документирует свою модель отдельно |
| `docker-compose.yml` ссылается на удалённые файлы | **устранён** | `backend/` восстановлен |
| `tests/` импортируют удалённый модуль | **устранён** | `aeza_analyzer/` восстановлен |
