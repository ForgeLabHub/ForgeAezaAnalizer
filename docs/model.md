# Модель риска оттока

## Почему rule-based, а не ML

В снимке **нет исторических исходов оттока**: нет событий отмены, нет метки «клиент
ушёл», нет даты ухода. Обучить классификатор и измерить его качество (precision,
recall, ROC AUC) не на чем, а значит любое заявление о точности было бы
необоснованным.

Поэтому используется прозрачный взвешенный скоринг. Интерфейс прямо сообщает: **балл
риска — не вероятность оттока в процентах.** При появлении истории исходов модель
можно заменить на калиброванную (см. «Путь развития»).

---

## Три разные сущности

Их легко перепутать, поэтому они разведены на уровне кода.

| Понятие | Что это | Статусы | Прогнозируется? |
| --- | --- | --- | --- |
| Текущее состояние | Что с услугой сейчас | `active`, `suspended`, `prolong_wait` | — |
| Состоявшееся событие | Уже произошло | `deleted`, `blocked` | **Нет** |
| Риск оттока | Вероятное неблагоприятное событие в будущем | — | Да, только для открытых услуг |

Услуги со статусами `deleted` и `blocked` **исключены из прогноза**. Они получают
категорию `not_applicable` и текстовое пояснение; балл им не присваивается. Прогноз по
уже удалённой услуге был бы бессмысленным.

В интерфейсе такие состояния показаны отдельно — в блоке «Почему клиент в этой
группе» как «Завершённые состояния (не прогноз)».

## Факторы риска

Каждый фактор нормализован в диапазон **0…1**. Ни один фактор не включается в модель
только потому, что «выглядит логичным»: у каждого проверены смысл и доступность в
данных.

| Ключ | Название | Как считается | Нормализация | Вес |
| --- | --- | --- | --- | --- |
| `expiry_proximity` | Близость даты окончания | `days_left = (expiresAt − now)` в сутках | 0 при `days_left ≥ horizon`; 1 при `days_left ≤ 0`; иначе `1 − days_left/horizon` | 3.0 |
| `auto_prolong_disabled` | Автопродление отключено | `autoProlong == false` | 1 или 0 | 2.0 |
| `insufficient_balance` | Недостаточно средств для продления | `ratio = balance / price` | `clip(1 − ratio, 0, 1)`; неприменим при `price = 0` | 2.0 |
| `prolong_wait_status` | Ожидание продления | `status == 'prolong_wait'` | 1 или 0 | 2.5 |
| `suspended_status` | Услуга приостановлена | `status == 'suspended'` | 1 или 0 | 1.0 |
| `renewal_failure_rate` | Доля неуспешных продлений | `not_performed / все prolong` в пределах 90-дневного окна | 0…1; 0 если по услуге нет продлений | 2.5 |
| `failed_renewals` | Неуспешные продления | Число `prolong`-транзакций со статусом `not_performed` | не участвует в рейтинге (**вес 0**) | 0.0 |

> `failed_renewals` сохранён в API для совместимости, но исключён из взвешенной суммы:
> его сигнал уже полностью учтён фактором `renewal_failure_rate`, и двойной учёт
> завышал бы риск. Поле помечено `deprecated=true` в определении модели.

**Про `suspended`.** Статус `suspended` означает отключение по требованию клиента,
при этом начисления продолжаются: это сигнал внимания, а не признак критического
оттока, поэтому его вес понижен до 1.0.

### Обработка отсутствующих данных

Фактор **не подменяется нулём**. Если значение вычислить нельзя:

- `insufficient_balance` — при `price = 0` (фактор неприменим);
- `failed_renewals`, `renewal_failure_rate` — если по услуге нет ни одной
  `prolong`-транзакции.

Такой фактор помечается как недоступный, его вес исключается из знаменателя, а
остальные веса фактически перенормируются. Пользователь видит причину пропуска в
карточке услуги, в блоке «Недостаточно данных».

**Различие между «нет неудач» и «нет истории».** Если по услуге есть продления и все
успешны, `failed_renewals = 0` — это измеренный факт. Если продлений нет вообще,
фактор недоступен, а не равен нулю: отсутствие записи не доказывает отсутствие
события.

## Формула

```
risk_score = 100 × Σ(weight_i × feature_i) / Σ(weight_i)
```

где суммирование идёт **только по доступным** факторам с положительным весом, а
`feature_i ∈ [0, 1]`.

Граничные случаи, покрытые тестами:

| Ситуация | Поведение |
| --- | --- |
| Сумма весов = 0 | `score = null`, категория `insufficient_data` |
| Все веса = 0 | То же; произвольный нулевой риск не подставляется |
| Отрицательный вес | Отклоняется валидацией (`RiskConfigError` / HTTP 422) |
| `NaN`, `±inf` | Отклоняются валидацией |
| Неизвестный ключ фактора | Отклоняется валидацией |
| Фактор недоступен | Исключается, веса перенормируются |
| `price = 0` | Фактор баланса неприменим |

### Пороги

| Диапазон | Категория |
| --- | --- |
| 0…34 | `low` — низкий |
| 35…64 | `medium` — средний |
| 65…100 | `high` — высокий |

Пороги хранятся централизованно (`DEFAULT_LOW_MAX`, `DEFAULT_MEDIUM_MAX`) и
настраиваются через `PATCH /api/v1/model/settings`. Инвариант
`0 ≤ low_max < medium_max ≤ 100` проверяется на сервере.

## Риск на уровне клиента

У клиента может быть несколько услуг. Простое усреднение замаскировало бы одну
критичную услугу за несколькими спокойными.

**Базовое правило: риск клиента — это максимум риска среди услуг, пригодных для
прогноза.** Это консервативная оценка: клиент считается в зоне риска, если хотя бы
одна его услуга в зоне риска.

Дополнительно по клиенту показываются:

- общее число услуг;
- число услуг, пригодных для прогноза;
- число услуг высокого риска;
- завершённые состояния (`deleted`, `blocked`) — отдельным счётчиком;
- стоимость продлений, попадающих под риск;
- конкретные услуги, сформировавшие оценку, с причинами по каждой.

**Риск и деньги разделены.** Дорогая услуга с низким риском не поднимает балл
клиента: `price` не входит в формулу риска. И наоборот — дорогая услуга с высоким
риском даёт большую выручку под риском, но не «больший риск». Это разные величины, и
интерфейс показывает их в отдельных метриках.

Если ни одна услуга клиента не пригодна для прогноза (все удалены или
заблокированы), клиент получает категорию `not_applicable` и `score = null`.

## Рекомендации по удержанию

Каждая рекомендация привязана к наблюдаемому сигналу в данных — не к общим советам.

| Сигнал в данных | Рекомендация |
| --- | --- |
| `expiresAt` в прошлом | «Просроченное продление» — выяснить планы клиента |
| `expiresAt` в пределах 7 дней | «Уведомить о скором окончании» |
| `balance < price` | «Проверить баланс» |
| `status == 'prolong_wait'` | «Проверить причину ожидания продления» |
| Есть `not_performed` продления | «Разобраться с неуспешным продлением» |
| `autoProlong == false` | «Обсудить включение автопродления» |

Рекомендации упорядочены по приоритету и дедуплицированы.

**Ограничения, отражённые в интерфейсе:** рекомендация не гарантирует удержание
клиента. Система не отправляет сообщения клиентам и не изменяет их аккаунты — она
предназначена для анализа и поддержки решений.

## Выручка под риском

Считается **отдельно** от риска (`app/domain/revenue.py`):

```
revenue_at_risk = стоимость ближайшего продления × risk_score / 100
```

Правила:

- учитываются только **открытые** услуги с `price > 0`;
- только продления, попадающие **внутри горизонта** (`AEZA_AS_OF` + `horizon_days`);
- одно продление учитывается один раз;
- услуги в состоянии `deleted`/`blocked` исключены;
- баланс клиента и `totalReplenished` в расчёт **не входят**;
- `transactions.amount` не используется (см. [`data.md`](data.md)).

В интерфейсе разделены четыре разные величины:

1. **выручка под риском** — прогнозная экспозиция;
2. **общая стоимость предстоящих продлений** — сумма без учёта риска;
3. **исторические пополнения** — справочно;
4. **число клиентов и услуг в зоне риска**.

Дата ближайшего продления определяется по `expiresAt` открытой услуги. Для статуса
`prolong_wait` оплаченный период уже истёк, поэтому такое продление ожидается сразу —
но в выручку под риском оно попадает только при наличии положительной цены и
открытого состояния.

**Ограничение:** снимок не содержит календаря будущих списаний. Даты продлений
выводятся из `expiresAt` и `paymentTerm`, поэтому это оценка на основе доступных
полей, а не бухгалтерский прогноз.

## Настраиваемость

`PATCH /api/v1/model/settings` принимает:

```json
{
  "horizonDays": 30,
  "weights": { "expiry_proximity": 5.0, "auto_prolong_disabled": 0.0 },
  "lowMax": 34,
  "mediumMax": 64
}
```

- частичное обновление: переданные поля заменяются, остальные сохраняются;
- веса валидируются (неотрицательные, конечные, известные ключи);
- горизонт — целое 1…365;
- пороги проверяются на инвариант;
- настройки хранятся на сервере (таблица `model_settings`), а не в браузере;
- после сохранения аналитика пересчитывается сразу.

`POST /api/v1/model/settings/reset` возвращает значения по умолчанию.

## Путь развития

Когда появятся исторические исходы, модель можно заменить, не меняя API:

1. Собрать датасет: по каждой услуге — вектор факторов на момент `T` и метка «отток
   произошёл в течение горизонта».
2. Обучить логистическую регрессию с теми же признаками — это сохранит объяснимость.
3. Откалибровать вероятности (Platt scaling / isotonic) и измерить качество на
   отложенной выборке по времени.
4. Заменить формулу, сохранив контракт ответа: `score`, `category`, `reasons`,
   `factors`. Интерфейс не изменится.
5. До появления валидированных метрик — не называть балл вероятностью.

Такой переход возможен именно потому, что скоринг централизован в одном модуле и
отделён от HTTP-слоя.
