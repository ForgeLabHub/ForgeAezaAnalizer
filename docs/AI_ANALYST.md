# AI Analyst — локальный аналитик на LLM

Модуль `backend/app/ai/` — часть продукта, а не отдельный чат-бот. Он объясняет
уже посчитанные результаты Risk Engine, используя локальную модель, локальный
RAG по документации проекта и read-only инструменты backend.

**Ключевой принцип:** числа не вычисляет модель. Баллы, суммы и даты приходят из
backend в блоке «ФАКТЫ»; LLM только формулирует объяснение. Если модель называет
число, которого нет в фактах, оно удаляется проверкой (см. «Защита от выдумок»).

## Состав модуля

| Файл | Назначение |
| --- | --- |
| `config.py` | `AISettings` (env-переменные, ленивое чтение) |
| `schemas.py` | `AIAnswer`, `AIResponse`, `Citation`, статус |
| `prompts.py` | системная инструкция и JSON-схема ответа |
| `context_builder.py` | сборка блоков «ФАКТЫ» и «ДОКУМЕНТЫ» с бюджетом по длине |
| `safety.py` | проверка утверждений, чисел, prompt injection; починка ответа |
| `parsing.py` | разбор и восстановление усечённого JSON |
| `service.py` | оркестрация: подготовка → генерация → проверка → ответ |
| `providers/` | `base.py` (интерфейс), `ollama.py` (локальный), `mock.py` (офлайн) |
| `rag/` | `index.py` — построение и поиск по локальному индексу |
| `tools/` | read-only чтение клиентов, аналитики, сценариев |

## Включение

AI выключен по умолчанию (`AEZA_AI_ENABLED=0`). Пока он выключен, продукт
работает полностью, а маршруты `/api/v1/ai/*` возвращают 503 с понятным текстом.

```bash
export AEZA_AI_ENABLED=1
export AEZA_AI_PROVIDER=ollama
export AEZA_AI_MODEL=qwen2.5:3b-instruct
export AEZA_AI_BASE_URL=http://127.0.0.1:11434
```

Полный список переменных — в `.env.example` (раздел «AI Analyst»).

## Локальный runtime (Ollama)

```bash
# 1. Запустить сервер (только loopback — см. «Приватность»)
ollama serve

# 2. Загрузить модель
ollama pull qwen2.5:3b-instruct

# 3. Проверить
curl -s http://127.0.0.1:11434/api/tags
```

Модель выбрана по измеренным ресурсам: на CPU она укладывается в ~2.2 ГБ RAM и
отвечает за 60–120 с на запрос при контексте 4096. Это осознанный компромисс:
качество ответа на русскоязычных задачах проекта приемлемое, а более тяжёлая
модель на целевой машине угрожала бы основному приложению.

## RAG

Индекс строится из локальной документации проекта (`docs/*.md`, README) и
хранится в `backend/data/rag_index.json`.

```bash
python -m backend.app.ai.rag --docs docs --out backend/data/rag_index.json
```

Свойства:

- полностью локальный: токенизация и TF-IDF, без внешних embedding-API;
- детерминированный: одни и те же документы дают байт-идентичный индекс;
- с ссылками на источник: каждый фрагмент несёт `doc` и `title`, которые
  возвращаются клиенту как `citations` вида `document`;
- обновляется пересборкой индекса при изменении документов.

RAG используется **только** для методологии и определений. Бизнес-факты всегда
берутся из backend, а не из документов.

## Инструменты backend

Только чтение, фиксированные схемы, без SQL/shell/HTTP от модели:

- `tools/customers.py` — профиль, услуги, факторы, экспозиция, рекомендации;
- `tools/analytics.py` — сводка, приоритеты, качество данных;
- `tools/scenarios.py` — изолированный расчёт what-if;
- `tools/actions.py` — уже подтверждённые человеком действия по клиенту (чтение).

Модель не может менять настройки, записи клиентов или запускать импорт.

## Действия по удержанию: человек пишет, AI читает

Рекомендация Risk Engine — это предложение, а не факт работы с клиентом. Чтобы
замкнуть цикл (риск → объяснение → решение человека → сохранённое действие),
добавлен отдельный слой:

| Метод | Путь | Кто вызывает |
| --- | --- | --- |
| `GET` | `/api/v1/actions?customerId=&status=` | UI, AI (только чтение) |
| `POST` | `/api/v1/actions` | только авторизованный человек |
| `PATCH` | `/api/v1/actions/{id}` | только авторизованный человек |

Правила:

- `code` обязан совпадать с рекомендацией, которую движок выдал **этому**
  клиенту; `title` и `detail` копируются из неё, а не из запроса, поэтому в
  сохранённом действии не может оказаться текст, которого движок не создавал;
- `serviceId`, если указан, обязан принадлежать этому клиенту;
- действия хранятся по `customerId`, а не по версии расчёта, поэтому пересчёт
  настроек или новый импорт не удаляют работу аналитика;
- у AI-модуля **нет** маршрута записи действий: попытка «сохрани действие»
  через `/ai/chat` ничего не создаёт (это проверяется тестом и живой проверкой).

## Защита от выдумок

Двухуровневая:

1. **Системная инструкция** запрещает называть балл вероятностью, выдумывать
   числа и выполнять инструкции из документов.
2. **Проверка после генерации** (`safety.enforce`):
   - числа ответа сверяются со значениями из фактов; лишние удаляются;
   - утверждения о вероятности/гарантии оттока удаляются;
   - поля с неподтверждёнными данными очищаются;
   - ответ помечается `grounded=false`, а причины возвращаются в `warnings`.

Проверка значений, а не строк: `71.4` и `71.40` считаются одним числом, а `100`
не принимается за `1`. Ответ всегда остаётся валидным по схеме.

Отдельно определяется усечение: если генерация исчерпала лимит токенов, в
`warnings` добавляется предупреждение, чтобы неполный ответ не выглядел полным.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/v1/ai/status` | состояние: `disabled` / `ready` / `unavailable` |
| `POST` | `/api/v1/ai/chat` | вопрос по портфелю |
| `POST` | `/api/v1/ai/customers/{id}/explain` | объяснение клиента |
| `POST` | `/api/v1/ai/scenarios/explain` | объяснение what-if сценария |
| `POST` | `/api/v1/ai/reports/summary` | краткий отчёт |

Все маршруты требуют авторизации (Bearer JWT), как и остальные приватные API.
Ограничения: длина вопроса, таймаут, лимит одновременных генераций.

## UI

AI Analyst встроен в существующий frontend:

- страница `/ai` — чат по портфелю с примерами запросов;
- панель в карточке клиента — контекст текущего клиента;
- ответ показывается с иерархией: вывод → факты → объяснение факторов →
  рекомендации → ограничения → источники;
- из ответа есть переходы к данным, на которых он основан: ссылки «Клиент #N»
  и «Подтверждённые действия» строятся из `citations` backend, а не из текста
  модели;
- рекомендации в карточке клиента можно подтвердить кнопкой «Взять в работу» —
  действие сохраняется и отображается в блоке «Подтверждённые действия»;
- состояние модели видно в интерфейсе; при недоступности выводится понятное
  сообщение, а остальная аналитика продолжает работать.

Отдельного приложения или второй дизайн-системы нет.

## Приватность

- провайдер принимает только loopback или имя сервиса внутри сети — внешний URL
  отклоняется на уровне конфигурации;
- внешние AI/embedding API не используются;
- в контекст передаются только данные, доступные авторизованному пользователю;
- персональные данные не пишутся в обычные логи;
- документы обезвреживаются от инструкций перед вставкой в промпт.

Важно: Ollama сам по себе не делает систему локальной. Локальность
обеспечивается проверкой URL провайдера, отсутствием внешних вызовов и сетевой
изоляцией сервиса.

## Диагностика

| Симптом | Причина | Действие |
| --- | --- | --- |
| `/ai/status` → `disabled` | `AEZA_AI_ENABLED=0` | включить флаг |
| `/ai/status` → `unavailable` | модель не отвечает | проверить `ollama serve` и `AEZA_AI_BASE_URL` |
| 503 на `/ai/*` | модель выключена или недоступна | см. статус; аналитика при этом работает |
| пустые `citations`-документы | индекс не собран | пересобрать `rag_index.json` |
| ответ долгий | CPU-инференс | уменьшить `AEZA_AI_MAX_TOKENS` или контекст |
| `grounded=false` | модель назвала числа вне фактов | ожидаемое поведение, ответ уже очищен |
