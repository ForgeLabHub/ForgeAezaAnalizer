# Отчёт аудита данных Aéza

Документ описывает **фактические** источники, структуру, объёмы и дефекты
данных организатора, а также решения по их обработке. Все числа получены
запуском импортёра и профилировщика (`python -m aeza_analyzer.cli import`,
`python -m aeza_analyzer.cli audit`), а не по названиям файлов.

## А. Найденные архивы

SHA-256 архива: `10af0815816e90e6cda8d84fe219a8696084c600d792acffa2317b876063c88f`.

Вложенных архивов нет. Архив распакован безопасно (проверка path traversal,
абсолютных путей, дубликатов имён, symlink-ов, коэффициента сжатия).

### Состав архива

```
датасет/
├── README.md           7 184 B   документация организатора
├── generate.py         5 801 B   генератор JSON и SQL (Python 3.10+)
├── test_generate.py    3 453 B   тесты генератора
├── data.json          32 081 B   данные: accounts / services / transactions
├── 001_schema.up.sql   2 373 B   DDL PostgreSQL (CREATE TABLE + CHECK + FK)
├── 001_schema.down.sql   169 B   откат (DROP TABLE)
└── 002_seed.sql       31 090 B   загрузка тех же данных в PostgreSQL
```

### Форматы данных

- **`data.json`** — единственный источник фактических данных: объект с
  массивами `accounts`, `services`, `transactions`. Именно он импортируется.
- **`002_seed.sql`** — те же записи в виде `jsonb_populate_recordset`;
  альтернативный путь загрузки в PostgreSQL, приложением не используется.
- **`001_schema.up.sql`** — контракт схемы (типы, CHECK, FK). Служит эталоном
  при валидации; модели приложения повторяют его ограничения.
- `generate.py` / `test_generate.py` — код организатора, **не исполняется**
  приложением.

Приложение читает **только `data.json`**. Остальные файлы — справочные.

## Б. Результаты анализа данных

### Объёмы и ключевые поля

| Набор | Строк | Столбцов | Уникальные id | Ключевые поля |
|-------|-------|----------|---------------|---------------|
| `accounts` | 10 | 7 | 10 | `balance`, `withdrawBalance`, `totalReplenished`, `bonusBalance`, `bonusState` |
| `services` | 30 | 9 | 30 | `ownerId`, `price`, `paymentTerm`, `autoProlong`, `status`, `createdAt`, `expiresAt` |
| `transactions` | 100 | 7 | 100 | `serviceId`, `amount`, `status`, `type`, `createdAt`, `performedAt` |

### Пропуски, дубликаты, аномалии

- **Пропусков нет** ни в одном обязательном поле.
- **Дубликатов нет**: email (10/10 уникальны), id во всех таблицах уникальны.
- `performedAt IS NULL` ровно у 33 транзакций — все они `not_performed`
  (инвариант схемы соблюдён).
- **Аномалий целостности нет**: `services_without_account = 0`,
  `transactions_without_service = 0`.
- Найдено **17 из 30 услуг с `expiresAt` раньше момента снимка** — это
  ключевой момент: почти половина «живых» строк относится к прошлому, а не к
  будущему. Это влияет на выручку под риском (см. ниже).

### Распределения

**Аккаунты** (значения в евроцентах):

| `totalReplenished` | 70 924 | 434 296 | 222 407.3 | 202 085.5 |
| `bonusBalance` | 1 535 | 9 863 | 5 852.0 | 5 033 |

`bonusState`: `locked` 5, `unlocked` 5.

**Услуги**:

| Поле | Значение |

**Транзакции**:

### Временные диапазоны

- `services.createdAt`: 2025-09-14 … 2026-10-19T14:30Z
- `services.expiresAt`: 2025-09-14T16:00Z … 2027-10-19T14:30Z
- `transactions.createdAt`: 2025-09-14T15:00Z … 2026-10-19T14:35Z
- **Момент снимка (`reference_at`), выведенный из данных:**
  `2026-10-19T14:35:53Z` — совпадает с опорной датой генератора
  (`2026-10-19T15:00:00Z`) с точностью до минут.

### Связи между сущностями

```
accounts.id  ←──  services.ownerId      (1 : N, ровно 3 услуги на аккаунт)
services.id  ←──  transactions.serviceId (1 : N, 3–4 транзакции на услугу)
```

Оба внешних ключа ссылочно целостны. Это **независимые таблицы одного
снимка состояния**, а не несколько версий одних данных: `data.json` и
`002_seed.sql` содержат идентичный набор, подтверждено сверкой.

### Денежные единицы

Согласно README организатора, денежные поля аккаунта и `price` хранятся в
**евроцентах**. Правило кейса «100 единиц = €1» применимо к этим полям и
**только** к ним:

- `balance`, `withdrawBalance`, `totalReplenished`, `bonusBalance` — евроценты;
- `services.price` — евроценты;
- `transactions.amount` — **не деньги в этой модели**: README прямо указывает,
  что `amount` генерируется независимо от `price` и ограничен диапазоном
  0–1000. Конвертация `amount` в евро для финансовых расчётов не применяется,
  чтобы не смешивать семантики.

Канонически всё хранится в целых евроцентах; в евро переводится один раз на
границе API.

## В. Найденные дефекты исходных данных и решения

| # | Наблюдение | Оценка | Решение |
|---|-----------|--------|---------|
| 1 | 17 из 30 услуг истекли до момента снимка | Не дефект, но важно: это «прошлое», а не прогноз | Исключены из выручки под риском; для риска срок «уже истёк» = максимальный сигнал срочности |
| 2 | `transactions.amount` не связан с `price` | Смешение семантик при наивной конвертации | `amount` не конвертируется и не используется как деньги в выручке |
| 3 | Нет полной истории пополнений (только `order`/`prolong`) | Нельзя восстановить когорты пополнений | `totalReplenished` берётся как есть, отдельно от баланса |
| 4 | Балансы не выводятся из транзакций | Расхождение возможно | Баланс и история не смешиваются; выручка считается от `price` |
| 5 | 6 услуг `deleted` (уже отток) | Прогноз будущего оттока не должен их включать | Вынесены в отдельный уровень `churned`, исключены из прогноза |
| 6 | Наименьшая единица сгенерирована как «ровный» синтетический набор (по 6 услуг каждого статуса, по 3 на аккаунт) | Данные синтетические, идеально сбалансированы | Зафиксировано как ограничение: модель не выдаётся за обученную |

Никакие исходные данные **не изменялись вручную** и не удалялись молча.
Оригинальный `датасет.zip` сохранён в репозитории без изменений.

### Воспроизводимое преобразование

Единственное преобразование, применяемое при импорте:

1. **Валидация** каждой записи против схемы (типы, диапазоны, ISO-8601 UTC,
   ссылочная целостность). Отклонённые строки **перечисляются с причиной**;
   при `strict=True` (по умолчанию) импорт прерывается целиком.
2. **Нормализация дат** в UTC (`...Z`, миллисекунды) — без смены значения.
3. **Денежные поля** остаются целыми евроцентами — без потерь.
4. Запись в SQLite в одной транзакции.

Сколько записей затронуто: 10 + 30 + 100 = **140**, отклонено **0**.
Все преобразования воспроизводимы: повторный импорт того же архива даёт тот же
результат (проверено тестом `test_reimport_is_idempotent`).

## Г. Как повторить аудит

```bash
python -m aeza_analyzer.cli import   # загрузка
python -m aeza_analyzer.cli audit    # профиль данных (JSON)
python -m pytest tests/ -v           # 48 тестов, включая аудит-инварианты
```

Профиль также доступен через `GET /api/audit` и вкладку **Data** в интерфейсе.
