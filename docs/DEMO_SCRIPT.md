# Сценарий демонстрации жюри

Пошаговый сценарий защиты решения (ТЗ, стр. 12: «найти клиента под риском,
объяснить причины и денежную оценку, изменить коэффициент или данные и показать
обновление результата»).

## Подготовка (до защиты)

```bash
cp .env.example .env
# задать в .env: AEZA_JWT_SECRET, AEZA_ADMIN_PASSWORD
docker compose up --build
```

Адреса:

| Что | Адрес |
|---|---|
| Панель | <http://localhost:8080> |
| API | <http://localhost:8000/api/v1> |
| Swagger | <http://localhost:8000/api/v1/docs> |
| Метрики | <http://localhost:8000/metrics> |

Если Docker недоступен — запускать API напрямую (см. [`DEPLOYMENT.md`](DEPLOYMENT.md)).

## Шаги демонстрации

### 1. Вход

Открыть панель → форма входа → логин и пароль администратора.
Показать, что **без входа панель недоступна** — это требование ТЗ (A14).

### 2. Dashboard

Показать сводку на реальных данных:

- 10 клиентов, 30 услуг;
- распределение по уровням: high / medium / low;
- отдельно — уже завершённые услуги (факт) и прогноз (не путать).

Акцент: цифры рассчитаны из датасета организатора, а не прописаны в вёрстке.

### 3. Найти клиента под риском

Открыть список клиентов → сортировка по risk score (по убыванию).
Взять первого: `user-0010@example.test`, score ≈ 73.3, уровень «Высокий».

Показать сортировку в обе стороны по: ID, email, балансу, сумме пополнений,
risk score (требование A4).

### 4. Карточка клиента

Открыть карточку. Показать:

- баланс, доступный к выводу, бонусы, сумма пополнений — **в евро**;
- риск-скор и уровень;
- услуги клиента с ценами и сроками;
- **причины риска**: «Близость даты окончания: услуга истекла 35 дней назад и
  не продлена» и другие;
- денежную экспозицию (revenue at risk).

Акцент: причины построены из фактических факторов, а не из общего текста.

### 5. Денежная оценка

Показать `summary`: сколько выручки под риском, сколько продлений предстоит,
как учитываются цены услуг, балансы и риск.

Объяснить горизонт (30 дней) и почему истёкшие продления не считаются будущими.

### 6. Изменение коэффициента (ключевой момент)

Открыть настройки модели. Изменить вес `expiry_proximity` с `3.0` на `0.5`.

Показать **без перезагрузки страницы**:

- риск-скор изменился;
- рейтинг клиентов перестроился;
- число клиентов высокого риска изменилось (2 → 1);
- денежная оценка пересчитана.

Акцент: это требование A6/A9 ТЗ — изменение коэффициента вызывает пересчёт.

### 7. Сброс

Нажать сброс настроек → значения вернулись к `3.0`, рейтинг восстановился.

Показать, что настройки **сохраняются после перезапуска** (A7): перезапустить
API и показать, что сохранённые значения остались.

### 8. Метрики

Открыть <http://localhost:8000/metrics>. Показать Prometheus-формат:
`aeza_customers_total`, `aeza_services_total`, счётчики запросов и ошибок.

Акцент: метрики согласованы с показателями панели (A10/A11).

### 9. Swagger

Открыть <http://localhost:8000/api/v1/docs>. Показать все обязательные
эндпоинты из ТЗ и возможность авторизации через Swagger.

### 10. Обновление данных

`PUT /api/v1/source/snapshot` — загрузить снимок данных, показать автоматический
пересчёт (A18: результат динамический).

## Резервные аргументы

| Вопрос жюри | Ответ |
|---|---|
| Это ML? | Нет. Объяснимая взвешенная модель — в датасете нет размеченных исходов оттока для обучения и валидации. |
| Почему не вероятность? | risk score — не вероятность: нет калибровки и статистической валидации. |
| Что с отсутствующими данными? | Фактор исключается, веса перенормируются, категория `insufficient_data` — не «низкий риск». |
| Почему две реализации? | Команда разрабатывала параллельно; основная — B (полное соответствие ТЗ), A сохранена как инструмент. См. [`ARCHITECTURE_DECISION.md`](ARCHITECTURE_DECISION.md). |
