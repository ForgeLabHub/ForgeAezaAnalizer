## 4. API

Реализованы и зарегистрированы все маршруты целевого контракта:

```
POST /api/v1/auth/login              GET  /api/v1/analytics/summary
GET  /api/v1/auth/me                 GET  /api/v1/model/settings
POST /api/v1/auth/logout             PATCH /api/v1/model/settings
GET  /api/v1/customers               POST /api/v1/model/settings/reset
GET  /api/v1/customers/{id}          GET  /api/v1/source/snapshot
PUT  /api/v1/source/snapshot         GET  /metrics
GET  /health                         GET  /api/v1/docs
GET  /api/v1/priority                POST /api/v1/scenarios/compare
GET  /api/v1/quality                 GET  /api/v1/analytics/events
GET  /api/v1/source/observations     GET  /api/v1/export/customers.csv
GET  /ready
```

Схема авторизации — `HTTPBearer`. Спецификация описывает только существующие
маршруты; наличие `/api/v1/priority` и `/api/v1/scenarios/compare` в `openapi.json`
проверено автоматическим тестом.

## 6. Что осталось и известные ограничения

### Ограничения данных (не дефекты)

- **Нет исторических исходов оттока** — модель rule-based, а не обученная и
  откалиброванная. Заявлений о точности нет ни в интерфейсе, ни в документации.
- **Нет динамики** — снимок описывает один момент. Вместо графика тренда показано
  актуальное распределение и прямо указано отсутствие истории.
- **Нет календаря будущих списаний** — даты продлений выводятся из `expiresAt` и
  `paymentTerm`; это оценка по доступным полям.
- **`transactions.amount` не связан с `price`** — сознательно не используется в
  расчётах.
- **Данные синтетические** — равномерное распределение статусов не имитирует реальную
  базу.

### Не проверено

- **Публикация в production не выполнялась.** Развёрнут только демонстрационный стенд
  (Compose с временным override-файлом). Домен, TLS-терминация на стороне Aéza,
  горизонтальное масштабирование и резервное копирование не настраивались.
- **Поведение на больших объёмах не измерялось.** Набор кейса — 10/30/100 записей.
  Сортировка и фильтрация выполняются в SQL, пагинация реализована, но нагрузочного
  тестирования не было.
- **Одновременный конкурентный импорт не тестировался.** Атомарность одного импорта
  проверена; сценарий двух параллельных импортов не воспроизводился.
- **Горизонтальное масштабирование не проверялось.** Один экземпляр API.

### Проверено в Docker

Стек из `docker-compose.yml` собран и запущен: все три контейнера перешли в состояние
`healthy`. Демонстрационный стенд доступен по публичному адресу из `docs/demo.md`.

| Проверка | Результат |
| --- | --- |
| `docker compose config` | Конфигурация валидна |
| Сборка образов | `project-api`, `project-web` собраны |
| Статус контейнеров | `db`, `api`, `web` — все `healthy` |
| Миграции применились | `SELECT count(*)` → `10 | 30 | 100` |
| API через nginx (порт 8080) | `/health` 200, `/` 200, `/api/v1/docs` 200 |
| Вход и сводка через nginx | Токен выдан; 10 клиентов, 18 открытых услуг |
| Совпадение с SQLite-прогоном | Идентичны **после сброса модели** (см. ниже): 5,80 €, 4 услуги высокого риска |
| Изменение веса на PostgreSQL | Услуг высокого риска 4 → 7, выручка 5,80 € → 7,72 € (совпадает с SQLite-прогоном) |
| Сохранение после `docker restart project-api-1` | `expiry_proximity = 9.0`, результат сохранился |
| Импорт корректного снимка | `accepted 10/30/100` |
| Отклонение некорректного снимка | HTTP 422, объёмы не изменились |
| `/metrics` через nginx | Агрегированные метрики; без токена 401 |

**Важное замечание о совпадении чисел.** Настройки модели хранятся в томе
`pgdata`, а не в образе. Пересборка (`docker compose up --build`) **не**
обновляет уже сохранённые веса, поэтому в существующем томе остались прежние
значения по умолчанию (`failed_renewals: 2.0`, `suspended_status: 2.0`,
`renewal_failure_rate: 1.5`). Из-за этого опубликованный расчёт расходился с
SQLite-прогоном: выручка под риском 5,74 € против 5,80 €, услуг высокого риска
3 против 4. После `POST /api/v1/model/settings/reset` оба окружения дают
одинаковые числа. Для нового окружения разница не проявляется (том пустой).
Шаг описан в README.

**Замечание по безопасности.** PostgreSQL в Compose использует пароль `aeza` по
умолчанию — это удобно для локальной демонстрации, но перед публикацией пароль и
`AEZA_JWT_SECRET` обязательно нужно заменить. Значения вынесены в `.env`.

## 7. Как воспроизвести

```bash
# Тесты
cd backend && python -m pytest tests/ -q

# Запуск API
cd backend
export AEZA_JWT_SECRET="$(python -c 'import secrets;print(secrets.token_urlsafe(48))')"
export AEZA_ADMIN_PASSWORD=demo123
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# Запуск интерфейса
cd frontend && npm install && npm run dev
```

Вход: `analyst@aeza.test` / `demo123`. Интерфейс: <http://127.0.0.1:5173>.
Опорный момент зафиксирован (`2026-10-19T15:00Z`), поэтому числа воспроизводимы.
