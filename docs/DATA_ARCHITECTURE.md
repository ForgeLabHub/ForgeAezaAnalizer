# Архитектура данных

Документ описывает **фактическую** архитектуру данных проекта: где хранятся данные,
как они попадают в систему, какие внешние потоки существуют и что именно проверено
запуском. Всё, что не подтверждено выполнением, помечено явно.

---

## 1. Две реализации в репозитории

В репозитории сосуществуют два независимых стека. Это историческое наследие
параллельной работы; важно не перепутать их при запуске.

| | Платформа (**основная**) | Наследие |
|---|---|---|
| Код | `backend/app/`, `core.py`, `main.py` | `aeza_analyzer/` |
| Зависимости | `backend/requirements.txt` | `requirements.txt` |
| Точка входа | `uvicorn backend.app.main:create_app --factory` | `./run.sh` |
| Запуск | `docker-compose.yml` (`api`, `web`, `db`) | локальный скрипт, SQLite |
| БД по умолчанию | `data/aeza.db` (`analyzer_*`) | `data/aeza.sqlite` |
| Тесты | `backend/tests/` (181) | `tests/` (69) |
| Документация | `docs/API.md`, этот документ | `docs/ARCHITECTURE.md`, `docs/API_PART_A_LEGACY.md` |

**Основная реализация — платформа `backend/app/`.** Именно её запускает
`docker-compose.yml`, её обслуживает `frontend/`, и именно её маршруты описаны в
`README.md` и OpenAPI.

`core.py` — это ядро **платформы** (его импортируют `backend/app/main.py`,
`storage.py`, `domain/module.py` и другие), а не наследия. Наследие
`aeza_analyzer/` подключено только к корневым тестам `tests/` и к `run.sh`.

`docs/ARCHITECTURE.md` описывает **наследие** (`aeza_analyzer/`) и не соответствует
структуре каталогов `backend/app/`. Читать его следует как описание второго стека,
а не платформы.

В каталоге `backend/data/` рядом лежат два файла разных стеков: `snapshot.json`
(снимок платформы) и `aeza.db` с таблицами `accounts` / `services` / `transactions`
(хранилище наследия). Платформа использует `snapshot.json` и `data/aeza.db`.

## 2. Хранилище

Хранилище одно — реляционная база. Отдельной очереди, кэша или второй базы нет.

| Окружение | URL | Статус проверки |
|---|---|---|
| Локальная разработка | `sqlite:///./data/aeza.db` (таблицы `analyzer_*`) | проверено запуском |
| Docker Compose | `postgresql+psycopg://aeza:aeza@db:5432/aeza` | **не проверено** (в песочнице нет Docker) |

Переключение — переменной `AEZA_DATABASE_URL`. Схема создаётся самим приложением
(SQLAlchemy `create_all`) при старте; отдельного шага миграций для платформы нет
(каталог `backend/app/migrations/` пуст).

### Таблицы

Схема версионированная: снимок источника, версия модели и результат расчёта хранятся
раздельно, а указатель `analyzer_current` определяет, что сейчас опубликовано.

| Таблица | Назначение | Ключ |
|---|---|---|
| `analyzer_current` | указатель на актуальные `generation` / `source_version` / `model_version` | `id` |
| `analyzer_sources` | версии входного снимка (полный JSON payload) | `version` |
| `analyzer_models` | версии настроек модели (веса, горизонт, пороги) | `version` |
| `analyzer_analyses` | версии расчёта: `source_version` + `model_version` + `as_of` + сводка | `generation` |
| `analyzer_customers` | денормализованный результат по клиентам для быстрой выдачи | `generation` + `customer_id` |
| `analyzer_service_index` | индекс услуг по статусам для фильтров | `generation` + `service_id` |
| `analyzer_observations` | наблюдения перехода статуса услуги между версиями снимка | `source_version` + `service_id` |
| `analyzer_audit` | кто и какое действие выполнил над расчётом | `generation` |
| `analyzer_users` | учётные записи аналитиков (хеш пароля, не пароль) | `id` |
| `analyzer_sessions` | активные сессии (хранение на сервере, не в браузере) | `id` |

Индексы по `analyzer_customers` покрывают сортировки из ТЗ: `risk_score`, `balance`,
`total_replenished`, `email`, `risk_category` — все вместе с `customer_id` для
устойчивого порядка.

Фактические объёмы в проверенном окружении: `analyzer_customers` — 10,
`analyzer_service_index` — 30, `analyzer_observations` — 30, `analyzer_sources` — 1,
`analyzer_analyses` — 1.

## 3. Внешние потоки данных

### 3.1. Источник кейса

Организатор указал публичную ссылку на Яндекс.Диск:

```
https://disk.360.yandex.ru/d/Pl8DQFxByaak1w   (пароль: hackathon-rnd)
```

**Статус: недоступно для автоматического получения.** Проверено 2026-10-23:

- `GET` публичной страницы → `302` на `showcaptcha` (капча).
- `GET cloud-api.yandex.net/v1/disk/public/resources?public_key=...` →
  `DiskSymlinkPasswordRequiredError` («Требуется пароль»).
- Скачивание через API требует интерактивного прохождения капчи и ввода пароля.

Программный обход капчи не выполнялся: это обход защиты чужого сервиса.

### 3.2. Что используется вместо него

В репозитории лежит готовый снимок, помеченный организатором как сгенерированный:

- `dataset/data.json` — 10 аккаунтов, 30 услуг, 100 транзакций;
- `dataset/generate.py` — генератор этих данных;
- `backend/data/snapshot.json` — **побайтово совпадает** с `dataset/data.json`
  (проверено сравнением JSON), это тот же снимок, который читает приложение.

Данные **синтетические**. Это не подмена реальных данных: кейс сам поставляет
сгенерированный набор. Проект нигде не выдаёт его за выгрузку из продакшена Aéza.

### 3.3. Схема источника

Три сущности в camelCase, связанные по целочисленным id:

| Сущность | Поля |
|---|---|
| `accounts` | `id`, `email`, `balance`, `withdrawBalance`, `totalReplenished`, `bonusBalance`, `bonusState` |
| `services` | `id`, `name`, `ownerId` → `accounts.id`, `paymentTerm`, `autoProlong`, `createdAt`, `expiresAt`, `status`, `price` |
| `transactions` | `id`, `amount`, `status`, `type`, `serviceId` → `services.id`, `createdAt`, `performedAt` |

Значения из данных: `paymentTerm` ∈ {`hour`, `week`, `month`, `quarter_year`,
`half_year`, `year`}; `status` услуги ∈ {`active`, `suspended`, `prolong_wait`,
`blocked`, `deleted`}; `status` транзакции ∈ {`performed`, `not_performed`};
`type` транзакции ∈ {`order`, `prolong`}.

### 3.4. Единицы денег

Все денежные поля источника — **целые в минорных единицах**, преобразование
`100 → €1` (евроценты). Преобразование выполняется один раз, в
`backend/app/domain/money.py`, и наружу деньги выходят парой `{cents, eur}`, где
`eur` — строка с двумя знаками после запятой. Баланс, бонусный баланс,
`totalReplenished` и цена услуги не смешиваются: это разные поля с разным смыслом.

`amount` транзакции в данных равен `0` и не выводится из балансов — это ограничение
источника, а не ошибка расчёта.

## 4. Импорт снимка

Единственный путь записи данных в основную реализацию — `PUT /api/v1/source/snapshot`.
Отдельного «фонового» импорта и внешних интеграций нет.

### 4.1. Последовательность

1. Тело проверяется Pydantic-схемой (`Snapshot`): типы, обязательные поля,
   неотрицательная цена, ISO-8601 UTC для дат, ссылочная целостность `ownerId` /
   `serviceId`.
2. При ошибке валидации возвращается `422` со списком `errors` и **ничего не
   записывается** — действующий снимок и расчёт остаются прежними.
3. При успехе снимок публикуется как новая версия `analyzer_sources`, и запускается
   пересчёт: новая запись `analyzer_analyses` и обновление `analyzer_current`.
4. Ответ содержит отчёт импорта: `snapshot.status`, счётчики `accepted` по сущностям
   и `rejected`.

### 4.2. Проверенное поведение

| Проверка | Команда | Результат |
|---|---|---|
| Отклонение некорректного снимка | `PUT` с `price: -5` | `422`, `errors[0].loc = ["body","services",0,"price"]` |
| Атомарность | после отказа прочитан `GET /api/v1/source/snapshot` | `generation 1`, `sourceVersion 1`, объёмы `10/30/100` — не изменились |
| Идемпотентность | повторный `PUT` того же `snapshot.json` | `200`; тот же `sourceVersion 1` (payload совпал), счётчики `10/30/100`, `rejected 0` |

То есть отказ не оставляет систему в частично обновлённом состоянии, а повторная
загрузка того же снимка не создаёт дубликатов.

### 4.3. Ограничения импорта

- Формат — только этот JSON-конверт (`accounts` / `services` / `transactions`).
  CSV, Excel и выгрузки из внешних CRM не принимаются.
- Дедупликация внутри одного снимка не выполняется: если в теле два аккаунта с одним
  `id`, это ошибка валидации, а не «последний побеждает».
- Ручного редактирования кода для импорта не требуется: данные подаются через API.

## 5. Что осталось непроверенным

| Пункт | Причина |
|---|---|
| Путь PostgreSQL | в песочнице нет Docker; Compose-стек не поднимался |
| Получение исходника с Яндекс.Диска | капча + пароль, программный доступ закрыт |
| Контейнеры `api` / `web` | Docker недоступен; запуск проверялся нативно (uvicorn + vite) |

Эти пункты не влияют на корректность расчётов: они касаются способа доставки
окружения, а не логики.
