# Архитектурный аудит

Дата: 2026-10-24. Ветка `feat/deployment-readiness`.

Документ описывает фактическую архитектуру, найденные дефекты и целевую
структуру. Массовый рефакторинг не выполнялся: перед защитой проекта
структурные перестановки дают меньше пользы, чем исправление подтверждённых
дефектов, а риск регрессии высок.

---

## 1. Фактическая архитектура

```
Пользователь → nginx (web) ──┬─→ /            → SPA (React, статика)
                             ├─→ /api/         → FastAPI (api:8000)
                             ├─→ /health       → FastAPI
                             ├─→ /ready        → FastAPI
                             └─→ /metrics      → FastAPI
                                        │
                                        ├─→ PostgreSQL  (аналитика: снимки, настройки, расчёты)
                                        └─→ SQLite      (пользователи и сессии, db/auth.sqlite3)
```

### Реальные точки входа

| Компонент | Точка входа | Роль |
| --- | --- | --- |
| Backend (канонический) | `uvicorn main:app` → `main.py` → `backend.app.main.create_app` | весь HTTP API |
| Аналитический движок | `AEZA_ANALYTICS_FACTORY=backend.app.domain.module:create` | риск, выручка, сценарии |
| Frontend | `frontend/index.html` + `vite build` → `dist/` | SPA |
| Compose | `docker-compose.yml` (db + api + web) | запуск стенда |
| Альтернативный auth | `backend/main.py` (`backend/auth/`) | отдельный модуль, **не** в Compose |
| Пакет `aeza_analyzer/` | `python -m aeza_analyzer.cli` | третья реализация, **не** в Compose |

### Какая реализация каноническая

Каноническая — `backend/app/`. Доказательства: только она собирается в
`backend/Dockerfile`, только её `main.py` поднимается Compose, только её
маршруты присутствуют в OpenAPI публичного стенда (18 путей, совпадает с
`origin/main`). `backend/auth/` и `aeza_analyzer/` сохранены как отдельные
задокументированные работы и не подключены к развёртыванию.

### Границы модулей

| Слой | Каталог | Содержимое |
| --- | --- | --- |
| HTTP | `backend/app/api/` | роутеры, схемы, сериализаторы, зависимости |
| Домен | `backend/app/domain/` | `risk.py`, `revenue.py`, `money.py`, `analytics.py`, `insights.py` |
| Контракт движка | `backend/app/modules.py`, `core.py` | `AnalyticsModule`, `CalculationAdapter`, публикация поколений |
| Хранилище | `backend/app/storage.py`, `db.py` | SQLAlchemy-модели, снимки, запросы |
| Конфигурация | `backend/app/config.py` | `Settings`, ленивое чтение окружения |
| Аутентификация | `backend/app/auth/` | JWT (HS256) и PBKDF2 |
| Метрики | `backend/app/metrics.py` | Prometheus-коллектор |

## 2. Найденные дефекты

| ID | Дефект | Доказательство | Серьёзность |
| --- | --- | --- | --- |
| A-1 | Экспорт CSV буферизовал весь отбор | 3.55 GiB и ~40 с на 50 000 строк | высокая — **исправлено** |
| A-2 | `X-Export-Rows` показывал всю базу вместо выборки | регресс при переходе на поток | средняя — **исправлено** |
| A-3 | Страницы экспорта не были прибиты к одному поколению | пересчёт в середине выгрузки склеивал снимки | средняя — **исправлено** |
| A-4 | Гонка при первой записи статуса рекомендации | 1 из 12 параллельных → 500 | средняя — **исправлено** |
| A-5 | `/ready` через nginx отдавал HTML SPA | `200` с `index.html` | средняя — **исправлено** |
| A-6 | Нет заголовков безопасности | `curl -D-` показал только `Server` | средняя — **исправлено** |
| A-7 | Пересчёт всей базы на каждый запрос | профиль: 100 страниц экспорта = 20 с | средняя — **открыто** |
| A-8 | `count(*)` повторяется на каждой странице экспорта | 0.037 с × 100 | низкая — **открыто** |
| A-9 | Нет ограничения попыток входа | 12 подряд → все 401 | высокая — **открыто** |
| A-10 | `AEZA_ALLOW_DEV_SECRET` по умолчанию `True` | `config.py:30` | средняя — **открыто** |

### Проверено и дефектом НЕ является

- Циклических импортов нет: `create_app()` собирает 13 маршрутов без ошибок.
- N+1 отсутствует: `customers()` и `customer()` читают готовые payload из
  таблицы результатов, а не обходят услуги и транзакции по одной.
- Фиктивных нулей нет: `UnavailableAnalytics` бросает `NotReadyError` → 503.
- Дублирования формул риска во frontend нет: UI только масштабирует ширину
  полос (`value * 100`), а score и суммы берёт из API.
- `transactions.amount` в выручке не участвует (см. `calculation-audit.md`).

## 3. Целевая архитектура

Текущее разделение слоёв уже соответствует целевому. Полезные улучшения —
локальные, без перестановки файлов:

1. **Один движок на все выходы.** Уже выполнено: API, дашборд, what-if, CSV и
   метрики читают один опубликованный результат расчёта
   (`storage.summary()` / `storage.customers()`), а не пересчитывают формулу.
   Держать этот инвариант при любых будущих изменениях.

2. **Кеш опубликованного результата.** `A-7` снимается кешем сводки и
   страниц на время жизни поколения. Внедрять только после подтверждения
   узкого места на целевом профиле, а не «на всякий случай».

3. **Один запрос вместо `count(*)` на страницу.** Мелкое улучшение
   `routes_export.py`: получить `total` один раз и передавать дальше.

4. **Ограничение частоты входа** (`A-9`) — требует хранилища счётчиков;
   вынести в отдельное решение, чтобы не трогать аутентификацию наспех.

5. **Безопасное значение по умолчанию** для `AEZA_ALLOW_DEV_SECRET` (`A-10`)
   с сохранением локального сценария из README.

## 4. Изменения, нецелесообразные перед защитой

| Изменение | Почему отложено |
| --- | --- |
| Слияние `backend/app`, `backend/auth`, `aeza_analyzer` | три независимые работы; слияние = большой риск регрессии без выгоды для демо |
| Переход на Redis/очереди | узкое место не подтверждено; противоречит правилу «не внедрять без доказательства» |
| Полный редизайн frontend | работает; точечные улучшения безопаснее |
| Микросервисное разделение | избыточно для одной БД и одного процесса API |
| Автоматические массовые действия по клиентам | меняет реальные данные, вне рамок задачи |

## 5. Риски изменения архитектуры

- `storage.customers()` используется списком, экспортом и инсайтами — смена
  его контракта затронет несколько выходов сразу.
- `core.py` управляет публикацией поколений; изменение порядка записи ломает
  атомарность и наблюдаемость (`SourceRow`/`ModelRow`/`AnalysisRow`).
- Метрики читают `storage.summary()` на каждый scrape; кеш должен сохранять
  согласованность с `generation`.
- `settings` читает окружение лениво — тесты полагаются на это; перезагрузка
  модулей сломает изоляцию тестов.
