### 2.3 Подтверждённые дефекты AI

### A-1 (высокая) — Изобретённое число в `limitations` не удаляется, хотя предупреждение утверждает обратное

**Доказательство [ФАКТ]:**
```python
ctx = "riskScore 71.4"
a = AIAnswer(summary="s", limitations="прогноз 99.9", ...)
c, r = enforce(a, context_text=ctx, risk_score=71.4)
# r.grounded == False, r.invented_numbers == ['99.9']
# c.limitations == 'прогноз 99.9 Ответ прошёл автоматическую проверку: ... удалены. ...'
# "99.9" in c.limitations  ->  True
```

**Причина:** `enforce()` (safety.py:214–235) очищает `facts`, `recommendations`, `summary`,
`factor_explanation`, но **не** `limitations`. При этом добавляет в `limitations` текст
«неподтверждённые числа и утверждения удалены».

**Влияние:** клиент получает выдуманную цифру **и** ложное заверение, что она удалена.
`check_numbers` её видит, `grounded=False`, но значение уходит в ответ и в UI.

**Рекомендация:** очищать `limitations` так же, как `summary` (заменить на безопасный
текст при найденных числах).

**Тест:** `enforce()` с числом в `limitations` → в результате нет этого числа.

### A-2 (средняя) — `citations` не проверяются на выдуманные числа

**Доказательство [ФАКТ]:** `check_numbers` перебирает `summary`, `factor_explanation`,
`limitations`, `facts`, `recommendations`. Поле `citations` (до 20 элементов, каждое с
`source` и `detail`) не проверяется.

**Влияние:** модель может вписать любую цифру в `citations[].detail`, и она дойдёт до
клиента без проверки. Формально это «источник», но UI показывает его пользователю.

**Рекомендация:** включать `citation.detail` и `citation.source` в проверку.

### A-3 (средняя) — `context.facts` возвращается клиенту целиком

**Доказательство [ФАКТ]:** `AIResponse.context["facts"] = prepared.context.facts_text`
(service.py:218) — это весь текст фактов, включая email клиента, балансы и список услуг.

**Оценка:** это осознанное решение («чтобы UI мог показать факты») и данные и так
доступны тому же пользователю через `/customers/{id}`. Но для `/ai/chat` с
`customerId` это дублирует персональные данные в ещё одном ответе, который может
попасть в лог клиента. Считать дефектом или решением — зависит от требований.

**Рекомендация:** подтвердить намерение; при необходимости отдавать `facts` только для
уже авторизованного просмотра того же клиента.

### A-4 (низкая) — `verify_grounding` в старом `llm.py` дублирует `safety.check_numbers`

Обе реализации проверяют числа, но по-разному: старая сравнивает строки и допускает
округление, новая — значения с допуском `1e-9`. Две разные политики grounding в одном
репозитории (см. §3).

## 4. `Core.update()` и публикация состояния

### 4.1 Как работает [ФАКТ]

`publish()` — compare-and-swap по `generation`:
```python
changed = session.execute(update(CurrentRow).where(
    CurrentRow.id == 1, CurrentRow.generation == previous.generation,
).values(generation=candidate.generation, ...))
if not changed.rowcount:
    return False
```
Всё внутри одной транзакции: `CurrentRow` → `SourceRow`/`ModelRow` → `AnalysisRow` →
`CustomerRow`/`ServiceIndexRow` → `ObservationRow` → `AuditRow`.

### 4.2 Проверки

| Вопрос | Ответ | Доказательство |
| --- | --- | --- |
| CAS гарантирован? | да, на уровне SQL `UPDATE ... WHERE generation = ?` | `storage.py:36–39` |
| Два параллельных изменения применяются? | да, оба, последовательно | прогон 2 потоков: `applied=[45,60]`, финал 60 |
| Audit не теряется? | нет, по строке на поколение | `audit: [(1,'system','source'),(2,'t45','model'),(3,'t60','model')]` |
| Частичный отказ? | вся транзакция откатывается | `database.transaction()` = `sessions.begin()` |
| Ошибка расчёта? | исключение до `publish`, состояние не меняется | `core.py:99` |
| Исчерпание 3 retry? | `ConflictError` | `core.py:105` |
| `expected_generation`? | сверяется и до, и после публикации | `core.py:81,103` |

### 4.3 Различие Python- и БД-атомарности [ФАКТ]

Атомарность обеспечивает **БД**, а не Python: `rowcount` из `UPDATE` — единственная
точка синхронизации. На SQLite это работает (проверено). На PostgreSQL с двумя
процессами CAS корректен по той же причине, но:

**[ГИПОТЕЗА]** при уровне изоляции ниже `SERIALIZABLE` возможна ситуация, когда оба
процесса читают `generation=N`, один публикует `N+1`, второй получает `rowcount=0` и
повторяет — это обработано retry-циклом. Проверить на живом PostgreSQL без его запуска
нельзя.

### 4.4 Дефект C-1 (низкая) — `recalculate` без изменений публикует новое поколение

Проверка `core.py:88` показала, что `recalculate=True` входит в условие публикации без изменений. Это создаёт рост данных и ломает семантику `generation` как версии.

```

                   auto_prolong_disabled 2.0×1.0=2.0
                   insufficient_balance 2.0×0.0=0.0   (доступен, значение 0)
                   prolong_wait_status 2.5×1.0=2.5
                   suspended_status 1.0×0.0=0.0       (доступен, значение 0)
```
