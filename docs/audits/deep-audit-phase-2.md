## 3. Telegram — подтверждённые дефекты

### T-1 (высокая) — Дедупликация не работает: `generation` всегда `None`

**Доказательство [ФАКТ]:**
```
tick 1: generation=2 high_risk_events=3   ключи: high_risk:None:5, high_risk:None:9
tick 2: generation=3 high_risk_events=3   ключи: high_risk:None:5, high_risk:None:9
tick 3: generation=4 high_risk_events=3   ключи: high_risk:None:5, high_risk:None:9
```

**Причина:** `main.dispatch_notifications` строит `analysis = calculation.calculate(storage.load())`.
`Core.update` добавляет `generation` в `summary` **после** `calculate()` (`core.py:100`),
поэтому у свежего `Analysis` поля `generation` нет — `notifications.py:62` берёт `None`.

**Влияние:** ключ вырождается в `high_risk:None:<id>`. Первое событие отправляется,
все последующие с тем же `(kind, customer)` подавляются **навсегда** — не на поколение,
а до ручной очистки таблицы. Уведомление о повторном переходе в высокий риск не придёт.

**Воспроизведение:** `build_events(analysis_from_calculate, previous=None)` → ключи с `None`.

**Рекомендация:** передавать `generation` из `storage.summary()` (или добавить его в
`Analysis.summary` внутри `Core.update` до публикации).

**Тест:** событие с `generation=2` и `generation=3` даёт разные `dedupe_key`; повторный
переход в high-risk на новом поколении отправляется.

### T-2 (средняя) — `previous` не передаётся: события строятся как «изменение», а сравнивать не с чем

**Доказательство [ФАКТ]:** `main.py:54` вызывает `notifications.dispatch(service, analysis,
settings=..., chat_id=...)` — параметр `previous` не передан. При `previous=None`:
`previous_customers` пуст → `was_high=False` → **все** high-risk клиенты считаются «перешедшими».

**Влияние:** при каждом вызове (каждый цикл пересчёта) генерируется событие для каждого
high-risk клиента. Спасает только дедупликация — которая сломана (T-1).

**Тест:** при двух подряд вызовах с одинаковыми данными второй даёт 0 событий.

### T-3 (средняя) — `generation` растёт каждые 60 с без изменения данных

**Доказательство [ФАКТ]:**
```
generation after import: 1 -> recalc1: 2 -> recalc2: 3
```
`Core.update(..., recalculate=True)` в цикле (`main.py:106`) увеличивает `generation`,
даже когда снимок и настройки не менялись, потому что `recalculate=True` форсирует
ветку публикации.

**Влияние:** `generation` — не идентификатор версии данных, а счётчик тиков. Любой
dedupe по поколению (после починки T-1) снова будет «новым» каждую минуту. Также
`AnalysisRow`/`CustomerRow` растут на 10 строк в минуту.

**Рекомендация:** при `recalculate=True` без изменения входа не публиковать новое
поколение — возвращать `previous` (как уже сделано для остальных случаев, `core.py:88`).

**Тест:** два `update(recalculate=True)` подряд без изменений → `generation` не меняется.

### T-4 (средняя) — Событие, отброшенное rate-limit, теряется навсегда

**Доказательство [ФАКТ]:**
```
A1 (key A): True
B1 (key B): False        # внутри окна 3600 с
B2 (key B retry): False  # строка уже существует
delivery rows: [('evt:B', 'rate_limited'), ('evt:A', 'sent')]
```

**Влияние:** при всплеске событий часть уведомлений теряется безвозвратно.

**Рекомендация:** при `rate_limited` удалять строку claim (или помечать и разрешать
повторную попытку позже).

**Тест:** отброшенное по лимиту событие отправляется при повторе после окна.

### T-5 (средняя) — Rate-limit per-process и не работает при нескольких воркерах

**Доказательство [ФАКТ]:** `service.py:96` — `self._last_send: dict[str, float]`,

**Рекомендация:** документировать как известное ограничение или перенести в БД/Redis.

## 6. `Core.update()` и публикация состояния

### 6.1 Как работает [ФАКТ]

`publish()` — compare-and-swap по `generation`:
```python
changed = session.execute(update(CurrentRow).where(
    CurrentRow.id == 1, CurrentRow.generation == previous.generation,
).values(generation=candidate.generation, ...))
if not changed.rowcount:
    return False
```
Всё внутри одной транзакции: `CurrentRow` → `SourceRow`/`ModelRow` → `AnalysisRow` →
`CustomerRow`/`ServiceIndexRow` → `ObservationRow` → `AuditRow`.

### 6.2 Проверки

| Вопрос | Ответ | Доказательство |
| --- | --- | --- |
| CAS гарантирован? | да, на уровне SQL `UPDATE ... WHERE generation = ?` | `storage.py:36–39` |
| Два параллельных изменения применяются? | да, оба, последовательно | прогон 2 потоков: `applied=[45,60]`, финал 60 |
| Audit не теряется? | нет, по строке на поколение | `audit: [(1,'system','source'),(2,'t45','model'),(3,'t60','model')]` |
| Частичный отказ? | вся транзакция откатывается | `database.transaction()` = `sessions.begin()` |
| Ошибка расчёта? | исключение до `publish`, состояние не меняется | `core.py:99` |
| Исчерпание 3 retry? | `ConflictError` | `core.py:105` |
| `expected_generation`? | сверяется и до, и после публикации | `core.py:81,103` |

### 6.3 Различие Python- и БД-атомарности [ФАКТ]

Атомарность обеспечивает **БД**, а не Python: `rowcount` из `UPDATE` — единственная
точка синхронизации. На SQLite это работает (проверено). На PostgreSQL с двумя
процессами CAS корректен по той же причине, но:

**[ГИПОТЕЗА]** при уровне изоляции ниже `SERIALIZABLE` возможна ситуация, когда оба
процесса читают `generation=N`, один публикует `N+1`, второй получает `rowcount=0` и
повторяет — это обработано retry-циклом. Проверить на живом PostgreSQL без его запуска
нельзя.

### 6.4 Дефект C-1 (низкая) — `recalculate` без изменений публикует новое поколение

- Логаут удаляет сессию из кеша.
- Токен проверяется по `sid` из claims + срок + `auth_version`.

## 10. Бизнес-инварианты

| Инвариант | Проверка | Результат |
| --- | --- | --- |
| Формула `100 × Σ(wᵢfᵢ)/Σwᵢ` | независимый пересчёт | **совпала** для всех услуг клиента №10 |
| Score клиента = max по услугам | сравнение | 71.4 = max(52.4, 71.4, 71.4) |
| Сумма весов 13.0 | `definition().defaults` | 13.0 |
| Deprecated-фактор не в сумме | `failed_renewals: 0.0`, `deprecated: True` | подтверждено; API отвергает вес ≠ 0 (422) |
| Пороги 34/64 включительно | `classify()` | ≤34 low, ≤64 medium, иначе high |
| Деньги — евроценты, `ROUND_HALF_UP` | `round_cents` на `Decimal` | подтверждено; `bool` отвергается |
| `revenue_at_risk = price × score/100` | чтение + тесты | подтверждено |
| Истёкшие услуги не в горизонте | `compute_service_exposure` | подтверждено; отдельный `overdue` |
| Одно продление один раз | `expiresAt` в `[now, now+H]` | подтверждено |
| `transactions.amount` не деньги | не используется в выручке | подтверждено |
| Сохранение настроек после рестарта | `test_integration` | покрыто |
| Контрольные значения | прогон | 71.4 / 5.80 € / 17.03 € |

**Контрольный пример вручную** (независимо от кода, услуга `service-0030`):

```
доступные факторы: expiry_proximity 3.0×1.0=3.0
                   auto_prolong_disabled 2.0×1.0=2.0
                   insufficient_balance 2.0×0.0=0.0   (доступен, значение 0)
                   prolong_wait_status 2.5×1.0=2.5
                   suspended_status 1.0×0.0=0.0       (доступен, значение 0)
недоступные:       failed_renewals (weight 0, excluded)
                   renewal_failure_rate (value None, excluded)

числитель = 7.5;  знаменатель = 3+2+2+2.5+1 = 10.5
100 × 7.5 / 10.5 = 71.428… → 71.4
```

Совпало с движком. Важное наблюдение: фактор, **доступный** со значением `0.0`,
остаётся в знаменателе (`insufficient_balance`, `suspended_status`), а фактор с
`value=None` — исключается целиком. Это ровно то поведение, которое описано в
`FactorDefinition.missing_data_behaviour` и подтверждает, что «неизвестно ≠ ноль».
