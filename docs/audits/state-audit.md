### Push заблокирован

```
$ git push --dry-run https://<token>@github.com/Pixelminds-hub/aeza-analizer.git ...
remote: Permission to Pixelminds-hub/aeza-analizer.git denied to Pavel1778.
fatal: ... error: 403
```

Токен принадлежит пользователю `Pavel1778` (проверено `GET /user`). Через API
репозиторий отдаёт `permissions: {push: true}`, но фактическая запись отклоняется:
создание тестовой ветки через API вернуло **403**. Токен — fine-grained без
разрешения `contents: write` на этот репозиторий.

**Следствие:** 10 коммитов, включая исправления этой сессии, существуют только
локально. Пробная ветка `audit-probe-delete-me` не создалась (проверено

## 3. Критическая находка: веса на стенде отличаются от кода и методологии

**Код** (`backend/app/domain/risk.py`, `DEFAULT_WEIGHTS`, сумма 13.0):

| Фактор | Вес |
| --- | --- |
| `expiry_proximity` | 3.0 |
| `auto_prolong_disabled` | 2.0 |
| `insufficient_balance` | 2.0 |
| `prolong_wait_status` | 2.5 |
| `failed_renewals` | **0.0** (deprecated) |
| `suspended_status` | 1.0 |
| `renewal_failure_rate` | 2.5 |

**Стенд** (`GET /api/v1/model/settings`, сумма 15.0):

| Фактор | Вес на стенде | Отличие |
| --- | --- | --- |
| `failed_renewals` | **2.0** | фактор, помеченный `deprecated`, **включён обратно** |
| `suspended_status` | **2.0** | вдвое больше согласованного |
| `renewal_failure_rate` | **1.5** | меньше согласованного |

Это не ошибка кода — код корректен. Это **сохранённые на стенде настройки**,
которые разошлись с согласованной методологией.

### Почему это важно

`docs/METHODOLOGY_SPEC.md` фиксирует решение владельца методологии:

> Оставить только `renewal_failure_rate`; `failed_count` — только для
> объяснений. Решение № 1; **устраняет двойной учёт 23.3 % веса**.

Стенд нарушает это решение: `failed_renewals` (2.0) и `renewal_failure_rate`
(1.5) считаются **одновременно**, то есть двойной учёт вернулся. На клиенте #10
это видно напрямую — service-0030:

```
failed_renewals        val=2.0  w=2.0  contribution=4.0
renewal_failure_rate   val=1.0  w=1.5  contribution=1.5
```

Оба фактора описывают одно событие (2 неуспешных продления из 2) и дают
5.5 из 15.0 — треть балла за один сигнал.

### API позволяет включить deprecated-фактор

Проверено: `PATCH /api/v1/model/settings` с `failed_renewals: 2.0` → **200**,
значение принято. `validate_settings` проверяет только числовой диапазон, но не
запрещает ненулевой вес у `deprecated`-фактора. Это и есть механизм, которым
стенд получил своё состояние.

## 4. Презентация не соответствует ни одному состоянию

Слайды содержат **73,3** для клиента #10 и **5,74 €**, а также переход
**73,3 → 81,0** при весе 15,0 → 21,0.

Воспроизведение запуском кода на официальном наборе:

| Конфигурация | Сумма весов | Клиент #10 | Выручка |
| --- | --- | --- | --- |
| Веса кода (по умолчанию) | 13.0 | **71.4** | **5.80 €** |
| Веса стенда | 15.0 | **85.2** | **5.74 €** |
| Веса стенда + `expiry_proximity` 9.0 | 21.0 | **89.7** | **7.48 €** |

Вывод: **денежные** числа слайдов (5,74 € и 7,48 €) соответствуют весам стенда,
а **баллы** (73,3 и 81,0) не воспроизводятся ни при одной проверенной
конфигурации. Ближайшее совпадение по деньгам даёт балл 85.2, а не 73.3.

Балл 73,3 не удалось получить ни перебором горизонтов (1–365 дней), ни
вариантами весов. Это означает, что слайды собраны на **промежуточной** версии
модели, которой в текущем коде уже нет.

**Риск для защиты:** если жюри откроет стенд, оно увидит 86,7 и 1453,09 €, а на
слайде — 73,3 и 5,74 €.

## 7. Живое обновление: реализовано и проверено

ТЗ требует: «После изменения данных или коэффициентов score, рейтинг и
денежные показатели обновляются автоматически, **без ручной перезагрузки
страницы**».

**До:** бэкенд отдавал SSE (`/api/v1/analytics/events`), но фронтенд его не
потреблял — страницы устаревали до нажатия F5.

**После:** добавлен `LiveProvider`, опрашивающий поколение анализа и
перезапрашивающий страницы при его смене.

Проверка в браузере на запущенном стеке:

| Шаг | Выручка | Балл service-0001 |
| --- | --- | --- |
| Исходно | 5,80 € | 38.4 |
| `expiry_proximity` 3 → 9 (через API, без reload) | **7,72 €** | **57.9** |
| Сброс к значениям по умолчанию (без reload) | **5,80 €** | **38.4** |

Обновление произошло без перезагрузки в обе стороны. Выбран опрос, а не SSE:
`EventSource` не умеет ставить заголовок `Authorization`, а передача токена в
query-строке записала бы credential в логи. ТЗ оставляет выбор механизма за
автором.

### Оговорка к требованию 4

ТЗ формулирует: «Панель показывает, сколько бизнес может потерять, **с учётом
стоимости услуг, балансов аккаунтов и риска**». Реализация считает
`revenue_at_risk = price × score/100`; баланс влияет на **риск** (через фактор
`insufficient_balance`), но не входит в сумму напрямую. Это осознанное решение
(сумма балансов — не потерянная выручка) и оно задокументировано, но формально
баланс в денежной сумме не участвует. Стоит проговорить это на защите как
обоснованный выбор, а не умолчать.
