# Аудит расчётов

Дата: 2026-10-24. Движок `aeza-heuristic-1.3.0`.
Источник кода: `backend/app/domain/risk.py`, `revenue.py`, `money.py`, `module.py`.

Формулы восстановлены из кода, а не из документации. Контрольные значения
воспроизведены запуском на официальном `dataset/data.json`.

---

## 1. Денежные единицы

Все денежные поля снимка — **целые евроценты**: `balance`, `withdrawBalance`,
`bonusBalance`, `totalReplenished`, `services.price`. Правило «100 единиц = €1»
совпадает с евроцентным соглашением, поэтому конверсия — одно деление на 100 и
выполняется **ровно один раз**, на границе API (`money.cents_to_eur`).

Единая точка округления — `money.round_cents` на `Decimal` с `ROUND_HALF_UP`.
Python `round()` (банковское округление) для денег не используется:
`round(62.5)` даёт 62, а финансы ожидают 63.

| Категория | Поле | Единица | Роль в расчёте |
| --- | --- | --- | --- |
| Основной баланс | `balance` | центы | доступен для продления |
| Выводимый баланс | `withdrawBalance` | центы | **исключён** из оплаты продления |
| Бонусы | `bonusBalance` | центы | учитывается только при `bonusState == "unlocked"` |
| Состояние бонусов | `bonusState` | строка | `unlocked` → бонус доступен |
| Исторические пополнения | `totalReplenished` | центы | только справочно, не выручка |
| Цена услуги | `price` | центы | основа будущего продления |
| Сумма транзакции | `transactions.amount` | центы | **не** используется в выручке |

`transactions.amount` в расчётах выручки не участвует: набор генерирует его
независимо от `price`. В фактор `renewal_failure_rate` входит только **факт**
неуспешного продления (`status == "not_performed"`), не сумма.

## 2. Доступные средства

`risk.py` (около строк 304–346):

```
bonus_available = bonusBalance if bonusState == "unlocked" else 0
spendable       = balance + bonus_available
feature         = clip(1 - spendable / price, 0, 1)
```

Правила:

- `withdrawBalance` **не** прибавляется — это реферальные средства для вывода;
- бонус входит только при подтверждённом `unlocked`; неизвестный `bonusState`
  трактуется как **недоступный**, поэтому отсутствие данных не завышает
  платёжеспособность;
- `price == 0` → фактор неприменим (`None`), а не ноль;
- при `spendable >= price` фактор равен 0; при нулевом балансе — 1.

Направление влияния: чем меньше доступных средств относительно цены, тем выше
риск. Отсутствие данных понижает уверенность, но **не** снижает риск.

## 3. Факторы риска

`risk.FACTORS`, веса по умолчанию (`DEFAULT_WEIGHTS`):

| Ключ | Смысл | Нормализация | Вес | В рейтинге |
| --- | --- | --- | --- | --- |
| `expiry_proximity` | близость окончания | `0` при `days_left ≥ horizon`; `1` при `≤ 0`; иначе `1 − days_left/horizon` | 3.0 | да |
| `auto_prolong_disabled` | автопродление выключено | `1` если `autoProlong == false` | 2.0 | да |
| `insufficient_balance` | не хватает средств | `clip(1 − spendable/price, 0, 1)` | 2.0 | да |
| `prolong_wait_status` | ожидание продления | `1` если `status == "prolong_wait"` | 2.5 | да |
| `failed_renewals` | число неуспешных продлений | диагностика | **0.0** | нет (deprecated) |
| `suspended_status` | услуга приостановлена | `1` если `status == "suspended"` | 1.0 | да |
| `renewal_failure_rate` | доля неуспешных продлений | `not_performed / все продления` в окне | 2.5 | да |

`failed_renewals` сохранён в API ради совместимости, но вес 0: сигнал уже
учтён в `renewal_failure_rate`, повторный учёт завышал бы риск.

`suspended` имеет вес 1.0 и не означает отток: по ТЗ это отключение по
требованию клиента, начисления продолжаются.

### Формула

```
risk_score = 100 × Σ(wᵢ × fᵢ) / Σ(wᵢ)      (risk.py:457)
```

Суммируются только доступные факторы (`value is not None` и `weight > 0`),
поэтому знаменатель — это сумма весов **применимых** факторов, а не всех.
Если `Σ(wᵢ) == 0` → `score = None`, категория `insufficient_data`
(не ноль).

### Пороги

`DEFAULT_LOW_MAX = 34`, `DEFAULT_MEDIUM_MAX = 64`; границы включительные:

```
score ≤ 34 → low;  score ≤ 64 → medium;  иначе → high
```

### Валидация настроек

`validate_settings` отклоняет: неизвестные ключи, отрицательные, нечисловые и
нефинальные веса, `horizon_days` вне `1..365`, инвертированные пороги
(`0 ≤ low_max < medium_max ≤ 100`). Нулевые веса разрешены — тогда score
деградирует до `insufficient_data`.

---

## 4. Три состояния не смешиваются

- **Открытые** (`active`, `suspended`, `prolong_wait`) — участвуют в прогнозе.
- **Завершённые** (`deleted`, `blocked`) — исключены из прогноза; клиент
  только с такими услугами получает `not_applicable`, а не `low`.
- **Денежная экспозиция** — считается отдельно и никогда не входит в score.

Цена услуги **не влияет** на риск: дорогая услуга не повышает likelihood.

---

## 5. Выручка под риском

`revenue.py`:

```
revenue_at_risk = scaled_cents(price, risk_score / 100)      (revenue.py:106)
```

Услуга учитывается, если одновременно:

1. `risk.eligible` и `score is not None`;
2. `price > 0`;
3. `now ≤ expiresAt ≤ now + horizon` (границы включительно).

Каждое продление считается **один раз**: услуга даёт не более одного
продления на горизонт. Уже истёкшие открытые услуги **не** включаются в
будущие горизонты — иначе непроверенное предположение выдавалось бы за
потерянную выручку. Они показываются отдельно как `overdue` (номинал для
разбора, не прогноз). `prolong_wait` дольше `PROLONG_WAIT_GRACE_DAYS = 5`
помечается как `lifecycle_inconsistent` — это сигнал о данных, а не об оттоке.

Горизонты отчёта: 7 / 30 / 90 дней.

### Что в показатель НЕ входит

`balance`, `withdrawBalance`, `bonusBalance`, `totalReplenished`, суммы
транзакций. Складывать их с выручкой нельзя: это разные категории
(деньги клиента против денег провайдера).

## 6. Контрольные расчёты

Запуск: `dataset/data.json`, `as_of = 2026-10-19T15:00:00+00:00`, веса по
умолчанию, `horizon = 30`.

| Показатель | Ожидалось | Получено | Совпало |
| --- | --- | --- | --- |
| Клиент №10, score | ≈ 71.4 | **71.4** | да |
| `revenueAtRisk` | ≈ €5.80 | **580 центов = 5.80 €** | да |
| Клиенты | 10 | 10 | да |
| Услуги | 30 | 30 | да |
| Транзакции | 100 | 100 | да |

Категории: `{low 0, medium 3, high 3, not_applicable 4}`.
Score по клиентам: 1→38.4, 4→35.4, 5→71.4, 6→34.6, 9→65.4, 10→71.4;
клиенты 2, 3, 7, 8 — `not_applicable` (только завершённые услуги).

Смена `expiry_proximity` 3.0 → 9.0: score 71.4 → 81.8, выручка 5.80 → 7.72 €.

### Расширенный набор (60 клиентов)

Seed добавляет 50 синтетических клиентов `demo-customer-*` к 10 официальным
`user-*@example.test`. На нём смена веса переводит клиентов через порог:
`high` 8 → 3 при снижении веса `expiry_proximity`. Это подтверждает, что
пороги работают, а не зафиксированы.

## 7. Детерминизм и границы

- `reference_at` выводится из данных (максимум `createdAt`/`performedAt`), а не
  из настенных часов, поэтому результат воспроизводим.
- Порядок строк не влияет на результат: агрегация идёт по ключам.
- Границы горизонта включительны с обеих сторон.
- `days_left` считается в сутках; календарные месяцы не подменяются
  фиксированным числом дней в факторе близости.
- Деление на ноль исключено: `price == 0` → фактор неприменим; `Σw == 0` →
  `score = None`.

---

## 8. Ограничения интерпретации

Score — **объяснимый правиловой индекс**, а не вероятность оттока. В наборе нет
исторических исходов оттока, поэтому обучение и калибровка невозможны.
`revenueAtRisk` — это `price × score/100`, то есть взвешенная стоимость
продлений, а не доказанный прогноз потерь. Уменьшение score в what-if не
означает фактически предотвращённый отток.
