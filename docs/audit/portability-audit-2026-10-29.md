## Дополнение: что нашёл первый прогон CI

Проверки писались вместе с кодом, но первый полный прогон `portability.yml`
на чистом раннере нашёл шесть реальных расхождений. Это и есть смысл матрицы:
не «у меня работает», а «сходится у всех».

| Симптом в CI | Настоящая причина | Что исправлено |
| --- | --- | --- |
| `openapi.json` расходится с приложением | в спецификацию не попали `APIKeyHeader` на `PUT /api/v1/source/snapshot`, схема `TestEmailRequest` и обновлённое описание `/api/v1/email/status` | файл перегенерирован; `export_openapi.py` пишет с `sort_keys=True` и сравнивает разобранный JSON, а не текст |
| `--check` мог «шуметь» сам по себе | сравнение шло по тексту, а порядок ключей зависит от версии pydantic | сравнение по структуре + отдельный шаг «генерация идемпотентна» |
| Compose стартовал без `POSTGRES_PASSWORD` | в `.env.example` стояло `change-me-too`, то есть пароль был всегда задан | значение в примере пустое, `${POSTGRES_PASSWORD:?}` теперь действительно обязателен |
| Smoke-тест падал на `/api/v1/analytics/overview` | такого маршрута нет; в приложении он называется `/api/v1/analytics/summary` | исправлен путь; добавлены проверки витрины `:8080`, которая проксирует API |
| Job'ы «первый старт» и «восстановление из бэкапа» падали по таймауту | проверка готовности шла через `docker compose exec python -c urlopen`, падала на первом же отказе и не сообщала состояние стека | единый `scripts/wait-for-http.sh` + смоук после восстановления и после `compose up` |
| `check_docs.py`: префикс API «не в .env.example» | переменной префикса в коде нет — документация описывала несуществующую настройку | `docs/api/conventions.md` говорит правду: префикс `/api/v1` задан в коде |

Дополнительно закреплена воспроизводимость зависимостей:
`backend/requirements.lock.txt` (40 пакетов) собирается целью `make lock` из
`backend/requirements.txt`, CI ставит по lock-файлу, если он есть.

## Дополнение: почему `main` был красным до этой ветки

Полный прогон `backend/tests` на чистом клоне `main` дал **480 passed,
12 failed**. Причины — две, и обе не связаны со сборкой:

### 1. Отключённая проверка OTP (исправлено отдельным PR)

В `backend/app/telegram/service.py` стояла заглушка:

```python
if False:  # TEMPORARY OTP TEST STUB: any six-digit code accepted
```

То есть любой шестизначный код привязывал Telegram к аккаунту. Восстановлено
сравнение pbkdf2-хеша через `hmac.compare_digest`; `test_telegram_bot.py` —
48 passed.

### 2. Официальный снимок данных был подменён демонстрационным

25 октября в `dataset/data.json` добавили демо-аккаунты: 10 → 41 аккаунт,
30 → 123 услуги. Приёмочные тесты написаны на официальный снимок
(`assert len(raw["accounts"]) == 10`), поэтому 11 тестов падали на числах:
`total == 10` против 41, `pages == 4` против 9, `revenueAtRiskEur == "5,80"`
против фактического и т. д. Логика была цела — расходились ожидания.

Проверка: с восстановленным официальным снимком весь набор даёт
**492 passed**. Поэтому:

- `dataset/data.json` — официальный снимок (10 аккаунтов), на него настроены
  тесты, документы и `.env.example`;
- `dataset/data.demo.json` — расширенный набор (41 аккаунт / 123 услуги),
  сохранён как отдельный файл для демонстраций, переключается переменной
  `AEZA_SNAPSHOT_PATH`.

Ничего не потеряно и не переписано «под тесты»: демо-данные живы, приёмка
снова доказуема, а расхождение теперь видно в конфигурации, а не в красном CI.
